# mkfix

FIX protocol testing engine built on [mkio](https://github.com/markuskimius/mkio) (async microservice framework) and [mkui](https://github.com/markuskimius/mkui) (Web Components UI framework).

## Quick start

```bash
pip install -e .
mkfix                    # starts on port 8080 with built-in config
mkfix -p 9090            # override port
mkfix -d mytest          # use mytest.db (auto-adds .db extension)
mkfix -d :memory:        # in-memory database, no persistence
```


## Architecture

mkfix builds its server with mkio's programmatic API: `create_app(cfg)` in `__main__.py` returns an `MkioApp`, which runs schema migration and service preflight before the event loop starts. The FIX TCP engine runs in the same asyncio event loop. FIX messages are written to SQLite via mkio's `WriteBatcher.submit()` with pre-compiled `CompiledOp` objects. The UI is an mkui app with custom pane types. UI commands flow through `FixCommandService`, a custom mkio `Service` subclass.

Key integration points:
- `create_app` / `MkioApp` — server bootstrap; `app.db` / `app.writer` / `app.change_bus` / `app.services` expose internals to the engine
- `app.add_service("fix_cmd", FixCommandService)` — custom service registration (not in TOML)
- `app.on_startup` / `app.on_shutdown` — no-arg async hooks; startup fires after services start, shutdown before they stop
- `WriteBatcher.submit(ops, params_list, data)` — batched writes from FIX engine
- `ChangeBus` — drives live UI updates when tables change
- `[static] "/" = "./static"` — mkio serves `index.html` at `/` and the directory's assets under `/static`; non-root routes (e.g. `/mkui`) serve at their own prefix

## FIX session protocol

The session state machine in `session.py` handles:
- Logon/Logout handshake (initiator and acceptor)
- Heartbeat and TestRequest exchange
- Sequence number tracking (`_rx_seq_num`, `_tx_seq_num`)
- ResendRequest on sequence gap, Logout on sequence too low
- SequenceReset/GapFill processing
- PossDupFlag (tag 43) — skips app message processing for retransmits
- ResetSeqNumFlag (tag 141) — must be processed before advancing rx_seq_num

The `FixServer` in `transport.py` reads the first message from each TCP connection to route by CompID pair. It re-serializes the Logon back into the parser buffer so the session can process it normally.

When a connection ends without a local stop (remote logout, drop), the reported status must match what the session is still doing: an acceptor returns to `LISTENING` (its listener stays registered and will logon again on the next inbound connection), while an initiator detaches its finished transport and reports `DOWN` — leaving the transport attached would make `start()`'s re-entry guard silently no-op. The initiator's retry-limit `ERROR` path detaches the same way.

## FIX dictionaries

Standard dictionaries (`STANDARD_VERSIONS` in `fix/dictionary.py`: FIX.4.0–FIX.5.0SP2) are generated JSON documents in `fix/dictionary_data/` — regenerate with `python tools/quickfix_to_json.py` (downloads the QuickFIX XML specs; NOTICE carries the license/acknowledgment). The converter merges `tools/overlays/<VER>.json` last: the FIX42 overlay preserves the curated display names the engine writes into DB rows and the blotter style rules test — `test_ui_config.py` asserts the overlay entries survive in the generated file, so regeneration can't silently rename them. Documents carry fields with types (`UTCTIMESTAMP` drives timezone display in the Details pane), enums, messages, ordered header/trailer, `begin_string` (what `sendprep` stamps in tag 8 — `FIXT.1.1` for the 5.0 dictionaries, whose header/trailer/admin messages are merged from FIXT11), and `groups` (counter tag → `delim` + `members`). Groups are display-only metadata for the Details tree — the engine still has no group model; order remains a sending concern (extra_tags), structure a parsing concern. The factory emits version-correct wire codes (`wire_exec_codes` in message.py): through FIX 4.2, fills go out as 150=1/2 alongside ExecTransType(20) and corrects/busts ride 20=2/1; from 4.3, tag 20 is withheld and fills/corrects/busts go out as 150=F/G/H (the engine records whichever code was actually sent, via `_sent_exec_kind`, and recognizes both dialects inbound). Tags the session dictionary doesn't define are withheld — 150/151 on 4.0, 141 on 4.0, 434 before 4.2 — body TransactTime(60) is dropped on D/F/G/9 before 4.2, CxlType(125)=F is added on a 4.0 OrderCancelRequest where it is required, and a FIXT.1.1 Logon carries DefaultApplVerID(1137) mapped from the app version. An accepted replace answers with OrdStatus(39)=5 where the dictionary defines it; FIX 4.4 removed that value (5.0 restored it), so there the ER and blotter carry the working status (New/PartiallyFilled/Filled) with ExecType=5 alone marking the event. All of it keys off `defines`/`has_enum`, so a custom dictionary that removes a tag stops it being emitted. The engine does not implement the FIXT session layer: a 5.0 session speaks 4.x-style session mechanics with FIXT.1.1 in tag 8.

Custom dictionaries live in the `fix_dictionaries` table: `doc` is JSON — a delta over `base_version` when set, a standalone full document otherwise. Merge semantics are `merge_dictionary` in dictionary.py, mirrored client-side by `mergeDictionary` in fix-dictionary.js (fields/messages/groups per tag with null removing, enums per tag per code union with null removing, header/trailer/begin_string wholesale). Rows are written only through `fix_cmd` (`save_dictionary`/`delete_dictionary`, plus `get_dictionary`/`list_dictionaries`) so the module-level registry in dictionary.py stays in step; `FixDictionary(name)` checks the registry before the shipped files, making a custom name valid anywhere a version string is accepted. The engine registers rows at startup (`_load_custom_dictionaries`, before sessions are built) and refuses to delete a dictionary any session's `dictionary` column names. Sessions bind by name: `fix_sessions.dictionary` (`''` = standard for the session's `fix_version`). `start_session` reloads config first, and `reload_session` rebuilds a stopped session's `FixSession` (dictionary and message factory are `__init__`-time wiring) while only swapping `config` on a running one — so a dictionary edit or rebind applies on next start, and a running session keeps its built dictionary until then. `dictionaries_list` (reqrep; `''` + standard names + custom rows via SQL UNION) feeds the session dialogs' Dictionary dropdown. Client side, `loadDictionary(name)` fetches standard versions from the `/dictionaries` static route and custom names through `fix_cmd get_dictionary` — the server resolves deltas, so client and engine can't disagree — caching per name; the Dictionaries pane calls `invalidateDictionary` after saving.

## UI panes

Blotter/viewer panes are declarative `mkio-table` configs in app.json. `raw-messages` sets `select: { state: "selected_message" }` so mkio-table mirrors the cursor's row into app state; `message-detail` subscribes to that path and renders the field breakdown. `fix_orders` stores raw FIX codes (`side_code`, `ord_type_code`) alongside display names so blotter buttons can send `fix_cmd` transactions with `${row.*}` interpolation. The client-side (order-blotter/trade-blotter, titled "Sent Orders"/"Received Trades") and market-side (market-order-blotter/market-trade-blotter, titled "Received Orders"/"Sent Trades") blotters share `orders_query`/`executions_query` and are split only by a `filter` on the `direction` column (`TX` = sent by this engine, `RX` = received); the titles state the direction directly. Received Orders drives everything through one Accept/Reject pair (`fix_cmd` ops `accept_request`/`reject_request`) plus Fill (`fill_order`): a new order arrives as `pending_action` "New", and inbound OrderCancelRequest (35=F) / OrderCancelReplaceRequest (35=G) park as "Cancel"/"Replace" with the request's ClOrdID and terms in the `pending_*` columns — `status` is untouched, so fills stay possible while a request is pending, and both buttons gate on `pending_action` alone. Fill gates on the non-dead statuses (`PendingNew`, `New`, `PartiallyFilled`, `Replaced`, and `Filled` — overfilling a done order is a scenario the engine must be able to produce; only `Canceled`/`Rejected` block it), always under the row's current ClOrdID — the chain's last accepted ID; filling a not-yet-accepted order consumes its pending New, since the fill ER implicitly acknowledges it. Sent Orders' Replace allows `Filled` too, so a filled order can be replaced up and revived. The dispatchers route to `accept_order`/`accept_cancel`/`accept_replace` and `reject_order`/`reject_cancel` (all also exposed as `fix_cmd` ops for scripting); accepting a cancel/replace sends an ER answering the request's ClOrdID (tag 11, with the superseded ID in tag 41, per the FIX chain) and moves the order row to that ClOrdID via the `rename_order` compiled op — on both sides a blotter row's ClOrdID always shows the chain's latest accepted ID, and the immutable `order_id` is the stable identity across the chain. Rejecting a request sends OrderCancelReject (35=9) with CxlRejResponseTo(434) and leaves the ClOrdID alone, and requests naming an unknown order are auto-rejected. The order upsert's SQL guards `order_qty`/`price` with `excluded`-based iif so an ER lacking tag 38/44 can't zero them. Sent Trades drives `correct_trade`/`bust_trade`, which ride ExecTransType(20) Correct/Cancel through FIX 4.2 and ExecType(150) TradeCorrect/TradeCancel from 4.3 on, always with ExecRefID(19) — the exec blotter is append-only, so corrections and busts add rows (`exec_type` "Correct"/"Cancel", or "TradeCorrect"/"TradeCancel" on 4.3+) rather than mutating fills. New orders are entered through the Sent Orders "New" button, which opens an mkui dialog; its session dropdown is fed by `sessions_list`, a reqrep service, because dialog `optionsFrom` uses request-reply and query services only answer subscriptions. The form is Symbol/Side/Quantity/Order Type/Price/TIF/Extra Tags — there is no Account field, an account rides as an extra tag (`1=...`). Replace opens the same form (session read-only; `session_id`/`orig_cl_ord_id` ride as `rowData`) prefilled from the row's as-submitted terms, so the values last entered — in New or the previous Replace — can be edited: `symbol`/`side_code`/`ord_type_code`/`tif_code`/`extra_tags` plus `entered_qty`/`entered_price` (`ENTERED_COLS` in engine.py). `send_new_order` writes them at insert and `send_cancel_replace` rewrites them through the `record_entered` op (a no-op for an unknown order — the request still goes out); they sit outside `ORDER_UPDATE_COLS`, so the counterparty's ERs never touch them, while `order_qty`/`price` remain the working terms an accepting ER sets. `entered_price` is NULL for market orders so the dialog opens with an empty price rather than 0, tag 59 goes on a cancel/replace only when `tif` is given, and `_backfill_entered_terms` seeds rows from before these columns from their working terms at startup. `session-blotter` is a standard `mkio-table` over `sessions_query` alone. That is only possible because the engine mirrors the live columns (`status`, `tx_seq_num`, `rx_seq_num`) onto `fix_sessions` as a second `CompiledOp` in the `upsert_state` write: an mkio query service with JOIN sql drops change events from non-primary watch tables (`query.py` `_listen_changes`), so a two-table join could never live-update — `fix_session_state` stays the state of record (it also keeps `error_text` and the timestamps), but the blotter reads only the mirror. Its buttons gate on the row's status through `enable.when` expressions — `ALL(rows, r -> ...)` on multi-select buttons so a mixed selection can't act on rows in the wrong state: Start, Edit, Delete, and Reset Seq only while stopped (`DOWN`/`ERROR` — `ERROR` counts as stopped, the session task has given up and can be restarted), Stop only while running/transitional. The same mirror trick gates order/trade actions on the owning session being up: `fix_orders`/`fix_executions` carry a `session_status` column, written at insert from the session's live status and re-mirrored by the engine on every status transition (`_mirror_session_status` — one update op per affected row, because the WriteBatcher publishes only one change event per op, so a whole-session UPDATE would live-update a single blotter row). Every button that acts on an existing order or trade (Replace/Cancel, Accept/Reject/Fill, Correct/Bust) tests `r.session_status == 'ACTIVE'` in its `enable.when` gate; Sent Orders' New is exempt since its dialog picks the session. The engine still enforces `_active_session` server-side — the UI gate just keeps dead buttons from being clickable. New/Edit/Reset Seq open dialogs declared inline in app.json; a dialog's field `name`s become the transaction payload, so they must match the op's TOML `fields` — Edit passes `session_id` and `enabled` as hidden `${row.*}` fields because the update op requires them but the user must not change them, and Reset Seq asks for the Tx/Rx sequence numbers and submits `fix_cmd` `reset_sequence`. The tall session form needs mkui 0.1.54 (earlier dialogs clipped a body taller than the default frame instead of growing); the blotter cell styling needs 0.1.55 — panes declare `styles` (per-column rule arrays) and `rowStyle` in app.json, which older mkui builds silently ignore; 0.1.56 stops paged tables from resizing columns on every page change (see mkio stream subscriptions); 0.2.0 moves everything conditional in app.json — style rules, `enable.when` gates, query `filter`s — to mkio's expression language (`value == 'Filled'`, `CONTAINS(['DOWN', 'ERROR'], r.status)`), the pre-0.2 `eq`/`in`/`match` rule keys and `rowMatch` being ignored without a warning; the floor is 0.2.2, whose Values | Range filter dropdowns (numeric columns auto-detect; value filters record exclude/include intent so live rows with unseen values pass an exclusion) reach the timestamp columns only through the `types` pane key — FIX-format stamps (`YYYYMMDD-HH:MM:SS.mmm`) are not ISO-8601, so every blotter/viewer timestamp column declares `{"type": "time", "parse": "%Y%m%d-%H:%M:%S.%f"}` (tz defaults to UTC, matching what the engine writes; the allocation viewer's `trade_date` uses `%Y%m%d`), which unlocks From/To bounds and the Today/Last hour/Last 15 min presets. Wire-sourced values at another precision (a seconds-only tag 60 from a pre-4.2 counterparty; a picosecond fraction exceeding `%f`'s 9 digits) don't parse and drop out of an active range filter unless its Include empty is ticked — engine-stamped columns are always milliseconds and immune. `test_ui_config.py` rejects the legacy rule keys and compiles every `when`/`filter` with `mkio.expr`, checks each `types` entry against the pane's columns and each engine-stamped timestamp column for a parse that matches `_fix_timestamp()` output, and `mkio.expect` in app.json pins `mkio` (0.x minor) and `expr` (exact language version) alongside the mkfix version. The colors reuse the VS Code-dark palette already in mkfix.css (`#4ec9b0` teal, `#6a9955` green, `#dcdcaa` yellow, `#f44747` red, `#858585` muted, `#569cd6` blue); rules test the displayed enum names (e.g. `Filled`, `SellShort`, `TX`), so renaming a display value means updating the matching style rules.

The Details pane (`message-detail`) translates through the owning session's dictionary: it keeps a live `sessions_query` map of session → dictionary name (the row's `dictionary` or its `fix_version`), falling back to the message's BeginString (except `FIXT.1.1`, which names no app version) and then FIX.4.2, and renders `parseMessageTree`'s output — repeating-group instances and header/body/trailer sections collapse (section state persists), columns drag-resize, and `UTCTIMESTAMP`-typed values plus the header timestamp render in a selectable timezone defaulting to the browser's; view prefs live in localStorage under `mkfix.detail.*`. `dictionaries` is a custom pane (dictionary dropdown + Fields/Enums/Messages/Groups/Wire tabs) driving the `fix_cmd` dictionary ops: edits mutate the working doc client-side (Δ marks delta entries; resolution mirrored by `mergeDictionary`), Save persists and invalidates the client cache, New/Clone offer linked-delta vs full-copy, Flatten converts derived→standalone, and Import/Export round-trip full documents (`<name>.json`) or deltas (`<name>.delta.json`, `mkfix_delta` marker). `test_ui_config.py` also guards the four copies of the standard-version list (dictionary.py, fix-dictionary.js, `dictionaries_list` sql, the session dialogs' options) against drift.

## Extra tags on outgoing messages

Every send action (`send_new_order`, `send_cancel`, `send_cancel_replace`, `accept_order`/`accept_cancel`/`accept_replace`, `reject_order`/`reject_cancel`, the `accept_request`/`reject_request` dispatchers, `fill_order`, `correct_trade`, `bust_trade`) takes an optional `extra_tags` string — pipe- or SOH-delimited `tag=value` pairs, parsed by `parse_extra_tags` in `message.py` into an ordered list that allows duplicate tags. That list is all a repeating group is on the wire (nested ones included) — order is a sending concern, structure only a parsing concern — so no group model or dictionary group metadata exists or is needed. The pairs ride on `FixMessage.extra` and are applied by `sendprep`, which now composes an ordered pair list (`_pairs`, what the serializers and `to_pipe_string` emit; `fields` stays the dict view for lookups). Placement rules: an empty value (`21=`) deletes the tag, even a computed one like 52; a tag appearing once in extras that the message would emit anyway is overridden in place (works on 34/49/52, and on 9/10 — the escape hatch for deliberately corrupt messages, which are otherwise recomputed); everything else appends in given order — header tags at the end of the header block, trailer tags before 10, the rest after the body. Tags are validated only as "numeric tag, has an `=`" — unknown/custom tags passing through untouched is the point of a test tool. Every blotter dialog carries the optional `extra_tags` field (the formerly one-click Cancel/Accept/Bust buttons became single-field dialogs using the same `rowData` + `submitPerRow` pattern as Fill, so multi-select still submits per row). Parsed messages (`parse_fix`, `FixStreamParser`) keep their ordered wire pairs on `_pairs` — duplicates included — so recorded raw strings and re-serialization are byte-faithful; `fields` stays the last-wins dict for lookups. The market side echoes inbound custom tags: `extra_pairs_of` (everything on a D/F/G that is neither header/trailer nor a `CONSUMED_ORDER_TAGS` member the engine maps to columns) is formatted by `format_extra_tags` onto the received order's `extra_tags` (and `pending_extra_tags` for whatever is pending — the D's own tags for a New, the F/G request's for a Cancel/Replace). The Accept/Reject dialogs prefill their Extra Tags field from `pending_extra_tags` and Fill from `extra_tags`, so inbound tags are shown for confirmation or editing and ride back on the answering ER; accepting a replace promotes the request's tags to the order's, and acting on a request (or a fill consuming the pending New) clears `pending_extra_tags`. Orders received before these columns existed are seeded at startup by `_backfill_rx_extra_tags`, which re-parses the recorded raw D (and pending F/G) messages — best-effort by ClOrdID match.

## ID scheme

All generated business IDs come from `fix/idgen.py`: `<2-char type code><2-char instance code><8-digit counter>`, e.g. `RTMA00000001`. Type codes: `RT` ClOrdIDs mkfix sends, `OR` Order IDs (received orders' also go out as OrderID tag 37), `EX` ExecIDs, `TR` Trade IDs. The instance code is the first two characters of the username, uppercased and padded with trailing X's, so concurrent mkfix users facing the same counterparty mint distinguishable IDs. Per-prefix counters start at 1, increment forever, and persist in `fix_id_state` (written through the WriteBatcher so they serialize with engine writes — no reissued IDs across restarts).

Identity rules the engine enforces:
- `fix_orders.order_id` is write-once: the upsert SQL guards it with an `iif` (like `order_qty`/`price`) so an inbound ER's OrderID(37) can't replace the locally minted OR id on a sent order. Sent orders get `order_id` at `send_new_order`; received orders at `_handle_new_order` (arrival, not accept).
- A ClOrdID chain advances on accept: `accept_cancel`/`accept_replace` answer the request's ClOrdID in tag 11 (superseded ID in 41) and rename the row; `_handle_execution_report` mirrors this on the client side by renaming 41→11 before upserting. The `rename_order` op no-ops if a row already holds the target ClOrdID (duplicate ER), keeping the `(cl_ord_id, session_id)` unique index safe.
- `fix_executions.trade_id` is the immutable trade identity: minted at fill, copied to corrections/busts (market side from the referenced execution row; client side by looking up ExecRefID(19) among recorded executions). Each correction/bust still gets a fresh ExecID — the exec blotter stays append-only.
- `correct_trade`/`bust_trade` resolve the order via the execution row's `order_id`, not its fill-time `cl_ord_id` — an accepted replace renames the chain, so the stored ClOrdID may no longer match any order row. The outgoing ER carries the order's current ClOrdID (tag 11), which the counterparty's renamed row matches.

## mkio stream subscriptions

`ref` is optional since mkio 0.1.55 — omitting it starts from the beginning of the buffer. Stream panes may also page backward with `before: true` + `maxcount`.

`raw-messages` sets `live: true` (mkui 0.1.52+) so it opens streaming instead of parked on today's first page. The start page still loads first, so `start: "today"` keeps its meaning; without that handoff the pane would replay the whole message buffer on open. Live stream panes follow the tail as of mkui 0.1.54 (jump to newest on going live, stay pinned while at the bottom, stop following once the user scrolls up) — before that, new messages rendered below the fold and looked like they were never sent. mkui 0.1.56 sizes a paged table's columns from its first page only: Earlier/Later/Refresh and the exit-live refetch no longer widen columns to fit the new page, so the Messages layout stays put while paging.

`tests/test_ui_config.py` guards app.json against the failure mode this config invites: dangling pane references, `index.html` imports of deleted modules, unknown service names, and a `mkio.expect.version` left behind by a release. It also statically checks the pane-module JS: imports must resolve (mkui paths against the installed `mkui.static_dir`), and services, transaction ops, and `fix_cmd` commands named in JS must exist server-side. These fail silently in the browser, so they are checked statically.

## mkio transaction defaults

Transaction service ops require explicit `defaults` in TOML config for any field that the client may omit. Fields listed in `fields` without a corresponding `defaults` entry are treated as required.

## Versioning

`mkfix/__init__.py` `__version__` is the single source of truth: pyproject.toml reads it via hatch dynamic version, and `_load_config` injects it as the server's reported version (mkfix.toml must not carry a `version` key). The one deliberate copy is in `static/app.json` (`mkio.expect.version` and the statusbar text) — it is the client build's baked stamp, so a stale cached client fails the handshake against an upgraded server. On a release bump, update `__version__` and the two app.json spots; `tests/test_ui_config.py` fails if they drift.

## Security notes

The Message Replay feature loads production FIX logs into test sessions, so files and hosts whose names carry `prod`/`production` may legitimately appear here — treat them with care: replayed production data stays on this machine and must never be committed, pushed, or sent to external services.

## Conventions

- Python 3.11+, type hints throughout
- No comments unless the why is non-obvious
- FIX tags are always string keys (e.g., `"35"`, not `35`)
- Timestamps use FIX format: `YYYYMMDD-HH:MM:SS.mmm` UTC. Outgoing wire timestamps (52/60) follow the session's `timestamp_precision` (`''` = protocol standard: seconds through FIX 4.1, milliseconds from 4.2; explicit second/millisecond/microsecond/nanosecond/picosecond override, sub-nanosecond digits zero-padded). The factory owns the resolved value (`FixMessageFactory.timestamp_precision`; `standard_precision` in message.py); DB timestamps stay milliseconds.
- Config is TOML (mkfix.toml), UI layout is JSON (app.json)
- Static JS uses vanilla ES modules, no build step
- Custom pane types registered via `window.Mkui.registerPaneType()`
