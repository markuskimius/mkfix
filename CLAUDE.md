# mkfix

FIX protocol testing engine built on [mkio](https://github.com/markuskimius/mkio) (async microservice framework) and [mkui](https://github.com/markuskimius/mkui) (Web Components UI framework).

## Quick start

```bash
pip install -e .
mkfix                    # starts on port 8080 with built-in config
mkfix -p 9090            # override port
mkfix -d mytest          # use mytest.db (auto-adds .db extension)
mkfix -d :memory:        # in-memory database, no persistence
mkfix -i Q7              # instance code stamped into generated IDs, remembered per database (-i '' forgets it)
```

## Architecture

mkfix builds its server with mkio's programmatic API: `create_app(cfg)` in `__main__.py` returns an `MkioApp`, which runs schema migration and service preflight before the event loop starts. The FIX TCP engine runs in the same asyncio event loop. FIX messages are written to SQLite via mkio's `WriteBatcher.submit()` with pre-compiled `CompiledOp` objects. The UI is an mkui app with custom pane types. UI commands flow through `FixCommandService`, a custom mkio `Service` subclass.

`serve()` does not call `app.run()`: it probes the web port first (`_check_port`), then mirrors `MkioApp.run` so the startup banner (`_banner` — Web UI URL, listen address, config and database paths, enabled sessions with role) prints only after the port is bound. The probe exists because mkio's `start()` runs the startup hooks (which open the database) before binding; a bind failure there leaves aiosqlite's non-daemon threads alive and the process hung, so losing the probe's race falls back to `os._exit(1)`.

Key integration points:
- `create_app` / `MkioApp` — server bootstrap; `app.db` / `app.writer` / `app.change_bus` / `app.services` expose internals to the engine
- `app.add_service("fix_cmd", FixCommandService)` — custom service registration (not in TOML)
- `app.on_startup` / `app.on_shutdown` — no-arg async hooks; startup fires after services start, shutdown before they stop
- `WriteBatcher.submit(ops, params_list, data)` — batched writes from FIX engine
- `ChangeBus` — drives live UI updates when tables change
- `[static] "/" = "./static"` — mkio serves `index.html` at `/` and the directory's assets under `/static`; non-root routes (e.g. `/mkui`) serve at their own prefix

## FIX session protocol

The session state machine in `session.py` handles:
- Logon/Logout handshake (initiator and acceptor)
- Heartbeat and TestRequest exchange
- Sequence number tracking (`_rx_seq_num`, `_tx_seq_num`)
- ResendRequest on sequence gap, Logout on sequence too low
- SequenceReset/GapFill processing
- PossDupFlag (tag 43) — skips app message processing for retransmits
- ResetSeqNumFlag (tag 141) — must be processed before advancing rx_seq_num
- Answering an inbound ResendRequest (`_answer_resend_request`) by replaying the recorded TX rows: `engine.sent_messages` returns the newest row per sequence number in the range; application messages go out again through `_retransmit` as `FixMessage.retransmit_copy` (same pairs and MsgSeqNum, 43=Y, the original 52 moved to 122, fresh 52, 9/10 recomputed), while runs of admin types (`ADMIN_MSG_TYPES`) and unrecorded numbers collapse into one SequenceReset-GapFill whose MsgSeqNum is the first number of the run — what the counterparty is expecting — and NewSeqNo the number after it (`_tx_seq_num` when the run reaches the end). Neither path goes through `_send`, so no new sequence number is spent; EndSeqNo 0 (or 999999 on 4.0/4.1) means through the last sent number, and a BeginSeqNo past it draws a session Reject. Sequence numbers recur across resets, so every reset of the outbound space (`reset_sequence_numbers`, `reset_on_logon`, an inbound Logon with 141=Y) records the current `fix_messages` id as `seq_epoch` in `fix_session_state` via `_reset_seq_space`, and the replay query only looks past it.
- A local stop of an ACTIVE session terminates the way the session protocol asks (`_initiate_logout`): a TestRequest first (`MKFIX-LOGOUT-<t>`), waiting up to one heartbeat interval for the Heartbeat echoing its TestReqID so the peer is known to have processed everything sent before it — the spec only recommends this step, so `logout_test_request` (session column, default 1) can switch it off, and a silent peer delays but never blocks the Logout; then the heartbeat loop is cancelled (after our Logout nothing goes out unsolicited), Logout is sent, status becomes `LOGOUT_SENT`, and `stop()` waits for the read loop to end — the peer's confirming Logout returns it (not answered, but persisted: their Logout consumed a number), a ResendRequest arriving first is still honored — or for the peer to drop, for at most `logout_timeout` seconds (column, default 0 = twice `heartbeat_interval`, the spec's recommendation), after which the socket closes as before. If the peer's EOF already ended the read loop before the stop, nothing is sent (`_connection_gone`). `FixEngine.stop` logs every session out concurrently so shutdown pays one timeout, not one per session.

The `FixServer` in `transport.py` reads the first message from each TCP connection to route by CompID pair. It pushes the Logon's wire bytes back into the parser buffer so the session can process it normally.

Messages are stored as their exact wire bytes: `FixMessage.raw` is set by the stream parser on receive and by `FixSocket.write` on send, and `record_message` (also the IOI/allocation inserts) writes `to_wire_string()` — the bytes decoded as latin-1, SOH delimiters included — into `raw_message`. `to_pipe_string` is a rendering only; storing it lost any `|` inside a value, and every parser split on `|`. `parse_fix` and the client's `splitFix` (fix-dictionary.js, used by `parseRawMessage`, `parseMessageTree`, `translateMessage`, and the Details pane) take SOH as the delimiter whenever one is present and fall back to `|` only for text without any — typed input, replay log lines, and rows recorded before 0.18, which stay readable but lossy. The Messages pane shows the column through a `display` template (`REPLACE(value, '\u{1}', '|')`) so the cell and the clipboard carry pipes while the stored value keeps SOH; `test_ui_config.py` compiles every `display` template and renders that one.

When a connection ends without a local stop (remote logout, drop), the reported status must match what the session is still doing: an acceptor returns to `LISTENING` (its listener stays registered and will logon again on the next inbound connection), while an initiator detaches its finished transport and reports `DOWN` — leaving the transport attached would make `start()`'s re-entry guard silently no-op. The initiator's retry-limit `ERROR` path detaches the same way.

## FIX dictionaries

Standard dictionaries (`STANDARD_VERSIONS` in `fix/dictionary.py`: FIX.4.0–FIX.5.0SP2) are generated JSON documents in `fix/dictionary_data/` — regenerate with `python tools/quickfix_to_json.py` (downloads the QuickFIX XML specs; NOTICE carries the license/acknowledgment). The converter merges `tools/overlays/<VER>.json` last: the FIX42 overlay preserves the curated display names the engine writes into DB rows and the blotter style rules test — `test_ui_config.py` asserts the overlay entries survive in the generated file, so regeneration can't silently rename them. Documents carry fields with types (`UTCTIMESTAMP` drives timezone display in the Details pane), enums, messages, ordered header/trailer, `begin_string` (what `sendprep` stamps in tag 8 — `FIXT.1.1` for the 5.0 dictionaries, whose header/trailer/admin messages are merged from FIXT11), and `groups` (counter tag → `delim` + `members`). Groups are display-only metadata; the engine has no group model. The factory emits version-correct wire codes (`wire_exec_codes` in message.py): through FIX 4.2, fills go out as 150=1/2 alongside ExecTransType(20) and corrects/busts ride 20=2/1; from 4.3, tag 20 is withheld and fills/corrects/busts go out as 150=F/G/H (the engine records whichever code was actually sent, via `_sent_exec_kind`, and recognizes both dialects inbound). Tags the session dictionary doesn't define are withheld — 150/151 on 4.0, 141 on 4.0, 434 before 4.2 — body TransactTime(60) is dropped on D/F/G/9 before 4.2, CxlType(125)=F is added on a 4.0 OrderCancelRequest where it is required, and a FIXT.1.1 Logon carries DefaultApplVerID(1137) mapped from the app version. An accepted replace answers with OrdStatus(39)=5 where the dictionary defines it; FIX 4.4 removed that value (5.0 restored it), so there the ER and blotter carry the working status (New/PartiallyFilled/Filled) with ExecType=5 alone marking the event. All of it keys off `defines`/`has_enum`, so a custom dictionary that removes a tag stops it being emitted. A 5.0 session speaks 4.x session mechanics with FIXT.1.1 in tag 8 (no FIXT session layer).

Custom dictionaries live in the `fix_dictionaries` table: `doc` is JSON — a delta over `base_version` when set, a standalone full document otherwise. Merge semantics are `merge_dictionary` in dictionary.py, mirrored client-side by `mergeDictionary` in fix-dictionary.js (fields/messages/groups per tag with null removing, enums per tag per code union with null removing, header/trailer/begin_string wholesale). Rows are written only through `fix_cmd` (`save_dictionary`/`delete_dictionary`, plus `get_dictionary`/`list_dictionaries`) so the module-level registry in dictionary.py stays in step; `FixDictionary(name)` checks the registry before the shipped files, making a custom name valid anywhere a version string is accepted. The engine registers rows at startup (`_load_custom_dictionaries`, before sessions are built) and refuses to delete a dictionary any session's `dictionary` column names. Sessions bind by name: `fix_sessions.dictionary` (`''` = standard for the session's `fix_version`). `start_session` reloads config first, and `reload_session` rebuilds a stopped session's `FixSession` (dictionary and message factory are `__init__`-time wiring) while only swapping `config` on a running one — so a dictionary edit or rebind applies on next start, and a running session keeps its built dictionary until then. `dictionaries_list` (reqrep; `''` + standard names + custom rows via SQL UNION) feeds the session dialogs' Dictionary dropdown. Client side, `loadDictionary(name)` fetches standard versions from the `/dictionaries` static route and custom names through `fix_cmd get_dictionary` — the server resolves deltas, so client and engine can't disagree — caching per name; the Dictionaries pane calls `invalidateDictionary` after saving.

## UI panes

Blotter/viewer panes are declarative `mkio-table` configs in app.json. `raw-messages` sets `select: { state: "selected_message" }` so mkio-table mirrors the cursor's row into app state; `message-detail` subscribes to that path and renders the field breakdown. `fix_orders` stores raw FIX codes (`side_code`, `ord_type_code`) alongside display names so blotter buttons can send `fix_cmd` transactions with `${row.*}` interpolation. The client-side (order-blotter/trade-blotter, titled "Sent Orders"/"Received Trades") and market-side (market-order-blotter/market-trade-blotter, titled "Received Orders"/"Sent Trades") blotters share `orders_query`/`executions_query` and are split only by a `filter` on the `direction` column (`TX` = sent by this engine, `RX` = received); the titles state the direction directly. Received Orders drives everything through one Accept/Reject pair (`fix_cmd` ops `accept_request`/`reject_request`) plus Fill (`fill_order`): a new order arrives as `pending_action` "New", and inbound OrderCancelRequest (35=F) / OrderCancelReplaceRequest (35=G) park as "Cancel"/"Replace" with the request's ClOrdID and terms in the `pending_*` columns — `status` is untouched, so fills stay possible while a request is pending, and both buttons gate on `pending_action` alone. Fill gates on the non-dead statuses (`PendingNew`, `New`, `PartiallyFilled`, `Replaced`, and `Filled` — overfilling a done order is a scenario the engine must be able to produce; only `Canceled`/`Rejected` block it), always under the row's current ClOrdID — the chain's last accepted ID; filling a not-yet-accepted order consumes its pending New, since the fill ER implicitly acknowledges it. Sent Orders' Replace allows `Filled` too, so a filled order can be replaced up and revived. The dispatchers route to `accept_order`/`accept_cancel`/`accept_replace` and `reject_order`/`reject_cancel` (all also exposed as `fix_cmd` ops for scripting); accepting a cancel/replace sends an ER answering the request's ClOrdID (tag 11, with the superseded ID in tag 41, per the FIX chain) and moves the order row to that ClOrdID via the `rename_order` compiled op — on both sides a blotter row's ClOrdID always shows the chain's latest accepted ID, and the immutable `order_id` is the stable identity across the chain. Rejecting a request sends OrderCancelReject (35=9) with CxlRejResponseTo(434) and leaves the ClOrdID alone, and requests naming an unknown order are auto-rejected. The order upsert's SQL guards `order_qty`/`price` with `excluded`-based iif so an ER lacking tag 38/44 can't zero them. Sent Trades drives `correct_trade`/`bust_trade`, which ride ExecTransType(20) Correct/Cancel through FIX 4.2 and ExecType(150) TradeCorrect/TradeCancel from 4.3 on, always with ExecRefID(19) — a trade is one row (`id`) and a correction or bust rewrites it as a new version (`update_execution`, keyed by the row id so pre-0.27 append-only chains need no index): the live row carries the trade's latest ExecID, `exec_ref_id` (the ExecID it answered, as tag 19 went out), `exec_type` ("Correct"/"Cancel", or "TradeCorrect"/"TradeCancel" on 4.3+) and terms, while the fill and each earlier correction stay in `fix_executions__history` as its versions. An ExecID is resolved by `_find_execution`: the live row first, then the history table, so a bust naming the original fill after a correction lands on the corrected trade rather than starting a new one; `_load_execution` uses the same lookup for scripted `correct_trade`/`bust_trade`. A busted trade is done — `_require_live_trade` refuses further corrections or busts by `exec_type` name (`BUSTED_EXEC_TYPES`; code 1 is Cancel on one dialect and PartialFill on the other) and the blotters' Correct/Bust/DK gates exclude the same names, with a muted `rowStyle` on busted rows. Received Trades drives `dk_trade` (DK button): a DontKnowTrade (35=Q) answering the counterparty's ExecutionReport with its own OrderID(37)/ExecID(17), DKReason(127) from a hand-listed dropdown (tested against the shipped dictionaries' 127 enums) and optional Text(58). It writes nothing — the trade row is the counterparty's report and stays as received; the DK shows in Messages — and OrderQty(38) comes from the order row found by the execution's fill-time ClOrdID, falling back to the ER's CumQty+LeavesQty when an accepted replace has since renamed the chain (`_order_qty_of`). An inbound 35=Q is only recorded as a message. New orders are entered through the Sent Orders "New" button, which opens an mkui dialog; its session dropdown is fed by `sessions_list`, a reqrep service, because dialog `optionsFrom` uses request-reply and query services only answer subscriptions. There is no Account field; an account rides as an extra tag (`1=...`). Replace opens the same form (session read-only; `session_id`/`orig_cl_ord_id` ride as `rowData`) prefilled from the row's as-submitted terms, so the values last entered — in New or the previous Replace — can be edited: `symbol`/`side_code`/`ord_type_code`/`tif_code`/`extra_tags` plus `entered_qty`/`entered_price` (`ENTERED_COLS` in engine.py). `send_new_order` writes them at insert and `send_cancel_replace` rewrites them through the `record_entered` op (a no-op for an unknown order — the request still goes out); they sit outside `ORDER_UPDATE_COLS`, so the counterparty's ERs never touch them, while `order_qty`/`price` remain the working terms an accepting ER sets. `entered_price` is NULL for market orders; tag 59 goes on a cancel/replace only when `tif` is given; `_backfill_entered_terms` seeds older rows at startup. `session-blotter` is a standard `mkio-table` over `sessions_query` alone. That is only possible because the engine mirrors the live columns (`status`, `tx_seq_num`, `rx_seq_num`) onto `fix_sessions` as a second `CompiledOp` in the `upsert_state` write: an mkio query service with JOIN sql drops change events from non-primary watch tables (`query.py` `_listen_changes`), so a two-table join could never live-update — `fix_session_state` stays the state of record (it also keeps `error_text` and the timestamps), but the blotter reads only the mirror. Its buttons gate on the row's status through `enable.when` expressions — `ALL(rows, r -> ...)` on multi-select buttons: Start, Edit, Delete, Reset Seq, and Change Seq only while stopped (`DOWN`/`ERROR` — the session task has given up and can be restarted), Stop only while running/transitional. The same mirror trick gates order/trade actions on the owning session being up: `fix_orders`/`fix_executions` carry a `session_status` column, written at insert from the session's live status and re-mirrored by the engine on every status transition (`_mirror_session_status` — one update op per affected row, because the WriteBatcher publishes only one change event per op, so a whole-session UPDATE would live-update a single blotter row). Every button acting on an existing order or trade gates on `r.session_status == 'ACTIVE'` (New is exempt); the engine still enforces `_active_session`. New/Edit/Change Seq open dialogs declared inline in app.json; a dialog's field `name`s become the transaction payload, so they must match the op's TOML `fields` — Edit passes `session_id` and `enabled` as hidden `${row.*}` fields, and Change Seq asks for the Tx/Rx sequence numbers and submits `fix_cmd` `reset_sequence`, while Reset Seq is a one-click transaction submitting the same op with literal `tx_seq_num`/`rx_seq_num` of 1 — a session reset: both numbers back to 1 and, through `_reset_seq_space`'s `seq_epoch` fence, no later ResendRequest replays anything recorded before it. Everything conditional in app.json — style rules (`styles` per-column rule arrays, `rowStyle`), `enable.when` gates, query `filter`s — is mkio's expression language (`value == 'Filled'`, `CONTAINS(['DOWN', 'ERROR'], r.status)`). Range filters reach the timestamp columns only through the `types` pane key — FIX stamps are not ISO-8601, so every blotter/viewer timestamp column declares `{"type": "time", "parse": "%Y%m%d-%H:%M:%S.%f"}` (UTC; the allocation viewer's `trade_date` uses `%Y%m%d`), which unlocks From/To bounds and the presets. The `filters` pane key sets the default views: Messages opens with `msg_type_name` excluding `Heartbeat` (an *exclusion*, so every unseen type still shows), and the four order/trade blotters open on a rolling `preset: "today"` range over their time column. The menus carry no `table.filter` views (the header filters cover them); `TestConfiguredFilters` still validates any that are added. Button `enable.when` gates are re-evaluated when a selected row is live-replaced or deleted, which Start/Stop and every `session_status` gate rely on. The declared floor is mkui 0.5.0 / mkio 0.7.0, the versions the UI is verified against; an older mkui ignores an unknown pane key or action with at most a console warning, so `test_ui_config.py` rejects the legacy rule keys, compiles every `when`/`filter` with `mkio.expr`, checks each `types` entry against the pane's columns and each engine-stamped timestamp column for a parse that matches `_fix_timestamp()` output, and `mkio.expect` in app.json pins `mkio` (0.x minor) and `expr` (exact language version) alongside the mkfix version.

The Details pane (`message-detail`) translates through the owning session's dictionary: it keeps a live `sessions_query` map of session → dictionary name (the row's `dictionary` or its `fix_version`), falling back to the message's BeginString (except `FIXT.1.1`, which names no app version) and then FIX.4.2, and renders `parseMessageTree`'s output — repeating-group instances and header/body/trailer sections collapse (section state persists), columns drag-resize, and `UTCTIMESTAMP`-typed values plus the header timestamp render in a selectable timezone defaulting to the browser's; view prefs live in localStorage under `mkfix.detail.*`. `dictionaries` is a custom pane (dictionary dropdown + Fields/Enums/Messages/Groups/Wire tabs) driving the `fix_cmd` dictionary ops: edits mutate the working doc client-side (Δ marks delta entries; resolution mirrored by `mergeDictionary`), Save persists and invalidates the client cache, New/Clone offer linked-delta vs full-copy, Flatten converts derived→standalone, and Import/Export round-trip full documents (`<name>.json`) or deltas (`<name>.delta.json`, `mkfix_delta` marker). `test_ui_config.py` also guards the four copies of the standard-version list (dictionary.py, fix-dictionary.js, `dictionaries_list` sql, the session dialogs' options) against drift.

## Saved layouts

The Layout menu is mkui 0.2.9's saved-layouts feature, which is opt-in per app: nothing appears unless the config carries a `layouts` block (constructs mkui's `LayoutManager` and registers the `layout.*` actions) *and* the menubar declares the entries (`layout.save`, a `{"layouts": true}` submenu for Restore, `layout.reset`). app.json has both, with `key: "mkfix"` so the store key doesn't ride on the app title. Because `mkio.url` is set, the store is the server: mkfix.toml declares the `mkui_layouts` table, the `mkui_layouts` transaction service (`save`/`delete` ops) and the `mkui_layouts_list`/`mkui_layouts_get` reqreps — the shapes `mkui init` scaffolds, minus the `access` pre-checks, which bind `:user` to a login mkfix does not have (mkio skips access checks entirely without `_mkio_users`). Every save therefore lands under owner `''`, the default history shared by everyone on the server. `test_ui_config.py` checks that the menu actions, the `layouts` block, and the three services stay together, since a missing half fails silently in the browser.

## Record history

`fix_sessions`, `fix_orders` and `fix_executions` are `versioned = true` (mkio 0.6): every change to a row lands in `<table>__history`, and the live row's `_mkio_version` is the cursor into that chain. The engine's ops needed no SQL change — mkio 0.6's writer owns the counter, comparing each `RETURNING *` row with the history row at its own version and recording a new one only when a versioned column changed, so a hand-written op is versioned like a compiled one and a write that changes nothing records nothing. The live mirrors are `unversioned` (`status`/`tx_seq_num`/`rx_seq_num` on sessions, `session_status` on orders and executions): absent from the history table, ignored by the changed-or-not comparison, and untouched by undo/redo, so heartbeats and session transitions record nothing. A session's history is its config edits, an order's its FIX lifecycle (one chain keyed by the immutable `id`, renames included), a trade's its fill, corrections and bust (one chain keyed by `id`, the same `trade_id` throughout). Startup runs migration before the engine's backfills, so a row a backfill touches shows pre-backfill values at version 1.

mkio writes no service for a history table, so mkfix.toml's "Record History" section declares, per table, a `<x>_versions` reqrep (one record's chain), `<x>_state` reqrep (live version and top, which arms Redo), `<x>_history` query over the history table (the feed mkui's History pane builds its table on, narrowed server-side by key, so the key is `filterable`), and as-of reqreps — split by direction (`sent_orders_as_of` etc.) because a pane's `filter` narrows only its live subscription. Each of the five blotters carries a `history` block naming those services, and every one of the five carries a `History` button (`unit: "row"`, action type `action`, `args.pane` naming the blotter it sits on — the `history` block alone brings Undo/Redo/As of… but not the timeline, per mkui's own example), the Edit menu (between Messages and Trading; `TestMenubar` pins the order and labels) leads with `edit.undo`/`edit.redo` labelled "Undo/Redo Session Change" since only sessions are undoable (no menu opens a history — `table.history` would open the timeline over whichever blotter's selection is current), and Sessions' block sets `columns` to the config columns so Diff and Blame skip the unversioned ones (blank in history rows) and labels `_mkio_version` "Ver" so it doesn't collide with the FIX version column. `TestRecordHistory` in `test_ui_config.py` checks every block's services, key, feed filterability, as-of direction, that no menu opens a history, and that each blotter's History button opens its own history.

Undo and redo are offered on Sessions only (`session_mgmt` `undo`/`redo` ops, `confirm` on): an undo rewinds only the local row — the counterparty's view of an order or trade does not move, and the next ExecutionReport would upsert over the restored version — so orders and trades stay read-only. A Delete is a real delete in mkio and takes the chain with it, so it cannot be undone. `FixEngine.handle_undo_redo`, registered with `app.on_undo_redo` in `__main__.py` before start (the engine is built in the startup hook, so the callback dispatches through the closure), follows a cursor move: an edit calls `reload_session` (rebuilds a stopped session, swaps config on a running one, as Edit does); an undone Add stops and drops the session and deletes its `fix_session_state` row via the `delete_state` op, since that table is not versioned; a redone Add inserts a DOWN state row and rebuilds. The undo button gates only on version state, so a running session's config undo applies on its next start, and on a baselined session at version 1 it deletes the row (behind the confirmation). `tests/test_engine.py` versions its tables as the server does (`load_config` + `history_specs` on the writer) and covers the chains, the mirrors recording nothing, and the hook's three shapes.

## Archiving

`mkfix archive`/`mkfix restore` (`mkfix/archive.py`, dispatched by `__main__.main` on the first argument) wrap mkio 0.7's row archiving. Tables come from `archive = {...}` keys in mkfix.toml: the five running-data tables are group `data`, archived by their FIX-stamped column (`timestamp`; `created_at` for orders) with `format = "%Y%m%d-%H:%M:%S.000"`; the config/state tables are group `config` — `fix_sessions` whole with `fix_session_state` as companion, `fix_dictionaries`/`fix_settings`/`fix_id_state`/`fix_replay_jobs` whole, `mkui_layouts` by `saved` — archived only when named. `tests/test_archive.py` requires every table to be archivable or a companion. Defaults: cutoff = local midnight today (`default_cutoff`), the data group, `--out ./archive`, short names via `ALIASES`; `-d/-p/--host` match the server and `server_answers` probes `/api/services` for `fix_cmd` to pick the mode — online through the server's `_mkio` archive request (`--url`/`--offline` force it), else on the file with the server assumed down. Runs preview, then prompt unless `-y`. Online runs pass `app.on_archive` → `FixEngine.check_archive` (refuses a session not `DOWN`/`ERROR`, a dictionary bound to a session not leaving in the same run, and `fix_id_state` while the engine holds the counters) and `after_archive` (drops session objects, `unregister_custom`). Restore is offline only and refuses while a server answers. Archived messages make a later ResendRequest into them a GapFill; a trade whose order is gone can't be corrected or busted.

## Extra tags on outgoing messages

Every send action (`send_new_order`, `send_cancel`, `send_cancel_replace`, `accept_order`/`accept_cancel`/`accept_replace`, `reject_order`/`reject_cancel`, the `accept_request`/`reject_request` dispatchers, `fill_order`, `correct_trade`, `bust_trade`, `dk_trade`) takes an optional `extra_tags` string — pipe- or SOH-delimited `tag=value` pairs, parsed by `parse_extra_tags` in `message.py` into an ordered list that allows duplicate tags. That list is all a repeating group is on the wire (nested ones included) — order is a sending concern, structure only a parsing concern — so no group model or dictionary group metadata exists or is needed. The pairs ride on `FixMessage.extra` and are applied by `sendprep`, which now composes an ordered pair list (`_pairs`, what the serializers and `to_pipe_string` emit; `fields` stays the dict view for lookups). Placement rules: an empty value (`21=`) deletes the tag, even a computed one like 52; a tag appearing once in extras that the message would emit anyway is overridden in place (works on 34/49/52, and on 9/10 — the escape hatch for deliberately corrupt messages, which are otherwise recomputed); everything else appends in given order — header tags at the end of the header block, trailer tags before 10, the rest after the body. Tags are validated only as "numeric tag, has an `=`" — unknown/custom tags passing through untouched is the point of a test tool. Every blotter action button is a dialog carrying the optional `extra_tags` field (`rowData` + `submitPerRow`, so multi-select submits per row). Parsed messages (`parse_fix`, `FixStreamParser`) keep their ordered wire pairs on `_pairs` — duplicates included — so recorded raw strings and re-serialization are byte-faithful; `fields` stays the last-wins dict for lookups. The market side echoes inbound custom tags: `extra_pairs_of` (everything on a D/F/G that is neither header/trailer nor a `CONSUMED_ORDER_TAGS` member the engine maps to columns) is formatted by `format_extra_tags` onto the received order's `extra_tags` (and `pending_extra_tags` for whatever is pending — the D's own tags for a New, the F/G request's for a Cancel/Replace). The Accept/Reject dialogs prefill their Extra Tags field from `pending_extra_tags` and Fill from `extra_tags`, so inbound tags are shown for confirmation or editing and ride back on the answering ER; accepting a replace promotes the request's tags to the order's, and acting on a request (or a fill consuming the pending New) clears `pending_extra_tags`. `_backfill_rx_extra_tags` seeds pre-existing received orders at startup from their raw messages.

## Write-before-send ordering

Every engine action submits its database writes *before* `session.send_message`. The send awaits several times (socket drain, `record_message`, `_persist_seq_nums`), so the read loop can process the counterparty's answer in between; sending first was a live race — an ER reaching `upsert_order` before `send_new_order`'s row existed took the INSERT branch (adopting the ER's OrderID as the write-once `order_id`) and then lost its status to the action's own upsert; on the market side an inbound cancel request parked `pending_action` only for the post-send `_write_order` to overwrite it; and an ER accepting a replace renamed the chain before `_record_entered` looked the order up. The WriteBatcher queue is FIFO, so writing first makes the order deterministic — `_write_order`'s docstring holds the rule for its callers. A failed send lands after the writes: `send_new_order` marks its row `Rejected` with `Send failed: …`. `tests/test_engine.py` guards this (`TestAnswerBeforeOwnWrite`, `TestRequestDuringMarketSend`), each class ending with a test that spies on `writer.submit` across every send path and asserts the send is the last event.

## ID scheme

All generated business IDs come from `fix/idgen.py`: `<2-char type code><2-char instance code><8-digit counter>`, e.g. `RTMA00000001`. Type codes: `RT` ClOrdIDs mkfix sends, `OR` Order IDs (received orders' also go out as OrderID tag 37), `EX` ExecIDs, `TR` Trade IDs. The instance code is the first two characters of the username, uppercased and padded with trailing X's, so concurrent mkfix users facing the same counterparty mint distinguishable IDs; `-i/--instance-code` (`serve(instance_code=)` → `FixEngine` → `IdGenerator`) overrides it with exactly two ASCII letters or digits used verbatim — `validate_instance_code` rejects anything else, at argparse time for the CLI and at construction otherwise. The override is sticky: `IdGenerator._resolve_saved_code` writes it to the `fix_settings` table (key `instance_code`, through the WriteBatcher) and a run without `-i` reads it back, so the code stays until `-i` names another or `-i ''` saves the empty value, which means "derive from the username" again; a saved value that fails validation (a hand-edited row) is ignored the same way. `None` (flag absent) thus differs from `''` (flag given blank) all the way down. The startup banner's `IDs:` line shows the code in effect and its source (`instance_source`: `saved` or `username`). Only newly minted IDs change: counters live per type prefix in `fix_id_state`, not per instance code, so switching the code mid-database continues the same count. Per-prefix counters start at 1, increment forever, and persist in `fix_id_state` (written through the WriteBatcher so they serialize with engine writes — no reissued IDs across restarts).

Identity rules the engine enforces:
- `fix_orders.order_id` is write-once: the upsert SQL guards it with an `iif` (like `order_qty`/`price`) so an inbound ER's OrderID(37) can't replace the locally minted OR id on a sent order. Sent orders get `order_id` at `send_new_order`; received orders at `_handle_new_order` (arrival, not accept).
- A ClOrdID chain advances on accept: `accept_cancel`/`accept_replace` answer the request's ClOrdID in tag 11 (superseded ID in 41) and rename the row; `_handle_execution_report` mirrors this on the client side by renaming 41→11 before upserting. The `rename_order` op no-ops if a row already holds the target ClOrdID (duplicate ER), keeping the `(cl_ord_id, session_id)` unique index safe.
- `fix_executions.trade_id` is the immutable trade identity: minted at fill and kept through corrections/busts, which are new versions of the fill's row (market side the row `_load_execution` found; client side the row ExecRefID(19) resolves to, live or through history — an unresolvable reference starts a new trade). Each correction/bust still gets a fresh ExecID, which becomes the live row's `exec_id` with the referenced one in `exec_ref_id`.
- `correct_trade`/`bust_trade` resolve the order via the execution row's `order_id`, not its fill-time `cl_ord_id` — an accepted replace renames the chain, so the stored ClOrdID may no longer match any order row. The outgoing ER carries the order's current ClOrdID (tag 11), which the counterparty's renamed row matches.

## mkio stream subscriptions

`raw-messages` sets `live: true` so it opens streaming instead of parked on today's first page; the start page still loads first, so `start: "today"` keeps its meaning (without that handoff the pane would replay the whole message buffer on open). Stream panes page backward with `before: true` + `maxcount`; `ref` is optional. Live panes follow the tail until the user scrolls up, and a paged table's columns are sized from its first page only.

`tests/test_ui_config.py` guards app.json against what fails silently in the browser: dangling pane references, `index.html` imports of deleted modules, unknown service names, a `mkio.expect.version` left behind by a release, and pane-module JS whose imports (mkui paths against the installed `mkui.static_dir`), services, transaction ops, or `fix_cmd` commands don't exist.

## mkio transaction defaults

Transaction service ops require explicit `defaults` in TOML config for any field that the client may omit. Fields listed in `fields` without a corresponding `defaults` entry are treated as required.

## Versioning

`mkfix/__init__.py` `__version__` is the single source of truth: pyproject.toml reads it via hatch dynamic version, and `_load_config` injects it as the server's reported version (mkfix.toml must not carry a `version` key). The one deliberate copy is in `static/app.json` (`mkio.expect.version` and the statusbar text) — it is the client build's baked stamp, so a stale cached client fails the handshake against an upgraded server. On a release bump, update `__version__` and the two app.json spots; `tests/test_ui_config.py` fails if they drift. The framework floors are pinned in four matching places — `pyproject.toml`'s `dependencies`, the README's Dependencies list (checked against pyproject), and `mkio.expect.mkio` in app.json, which the server compares by 0.x minor, so an mkio minor bump that leaves it behind paints the statusbar red with "Server version mismatch" while the app otherwise works. `expect.expr` pins `mkio.expr`'s `LANGUAGE_VERSION` exactly and moves only when the expression language does.

## Security notes

The Message Replay feature loads production FIX logs into test sessions, so files and hosts whose names carry `prod`/`production` may legitimately appear here — treat them with care: replayed production data stays on this machine and must never be committed, pushed, or sent to external services.

## Conventions

- Python 3.11+, type hints throughout
- No comments unless the why is non-obvious
- FIX tags are always string keys (e.g., `"35"`, not `35`)
- Timestamps use FIX format: `YYYYMMDD-HH:MM:SS.mmm` UTC. Outgoing wire timestamps (52/60) follow the session's `timestamp_precision` (`''` = protocol standard: seconds through FIX 4.1, milliseconds from 4.2; explicit second/millisecond/microsecond/nanosecond/picosecond override, sub-nanosecond digits zero-padded). The factory owns the resolved value (`FixMessageFactory.timestamp_precision`; `standard_precision` in message.py); DB timestamps stay milliseconds.
- Config is TOML (mkfix.toml), UI layout is JSON (app.json)
- Static JS uses vanilla ES modules, no build step
- Custom pane types registered via `window.Mkui.registerPaneType()`
