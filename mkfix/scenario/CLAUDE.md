# mkfix/scenario — the scenario language

A small language for acting on orders as events arrive. This directory holds the language — words, parser, checker, bundled examples — and what runs it: the interpreter, the runner and their clock. All three kinds of block run. The engine side it all stands on is in `../fix/CLAUDE.md`.

`check(text, templates=None, sessions=None) -> (Scenario, [Diagnostic])` is the way in. It never raises on a bad script: every problem comes back as a `Diagnostic(line, col, end, message, severity)` — lines from 1, columns from 0 — which is what the editor underlines. `errors(diagnostics)` are the ones that stop a script being armed or run; a `warning` does not.

## Shape of a script

`scenario NAME`, optional `seed N` and `on error continue`, then blocks. Blocks by indentation (spaces only), one statement per line, `#` comments. Three kinds of block, `Block.kind`:

| Header | kind | The order is |
|---|---|---|
| `on order [where EXPR]` | `market` | one we received; verbs accept, reject, fill, unsol cxl, restate, correct, bust, renotify |
| `run [on SESSION]` | `client` | one the script sends with `new`; verbs new, replace, cancel, dk. Without `on SESSION` the session is chosen at Run… (`Scenario.needs_session`) |
| `on sent order [where EXPR]` | `attached` | one sent some other way (by hand, Message Replay); client verbs except `new` |

One order per script instance. Everything that computes a value is an mkio expression (language 2: `and or not in`, durations as seconds), evaluated in `functions.ENV` — the defaults plus the opt-in `scenario` library (`TICK`, seeded `RANDOM`), which app.json's expressions can never see.

## Files

- `vocab.py` — **the single source of words**: `VERBS` (name → engine op, sides, terms → payload keys, required terms, whether it takes a trade target), `EVENTS` (sides, whether it carries a trade), `STATEMENTS` (form + help), `ENUMS` (bare words for side/type/tif/handl_inst/reasons → FIX codes; held to app.json's dialog options by a test), and the schemas `check_fields` checks expressions against (`scope_schema`, `match_schema` — order and trade fields are read from `mkfix.toml`'s table columns, so a new column is known at once). `vocabulary()` is all of it as plain data, help text included, for the editor and the reference pages. Nothing else may list these words.
- `parser.py` — lines → `nodes`. A `_Line` cursor takes words and phrases; expressions are parsed **in place, on the line's own text**, with `expr.parse_prefix`, which ends at a comma, one of our keywords, `±`, or the `#` of a comment — so an expression cannot run onto the next line and node positions are columns. `wait … where EXPR or timeout D` passes `stop=("or timeout",)`; the `+/-` spelling of jitter is fenced off with `until`. A bad line is reported and skipped, a bad compound line takes its body with it, and parsing goes on: the editor shows every problem at once.
- `check.py` — meaning: verb and event against the block's side, terms against the verb, required terms (unless `using` a template), trade targets (a trade verb needs `last trade` / `first trade` / `trade where …` unless it sits under a `when` whose events all carry a trade), every expression compiled and its field paths checked, `${…}` inside quoted values checked as templates (`Expr.template`), templates and sessions when the caller knows them. `let` and `with` names are known block-wide — a script has one flat scope per order, and `let` on a name that exists changes it.
- `nodes.py` — the tree; `walk(body)` and `expressions(statement)` are how everything else traverses it.
- `examples/*.scenario` — shipped in the wheel, read-only, opened as copies. Each opens with `# Title`, a bare `#`, then `Shows` / `Needs` / `Watch` / `Outcome` lines the Help page will be built from. They are the acceptance set: `tests/test_scenario.py` requires each to check clean and the set to use every market-side verb, event, statement, trade target, context name and both scenario functions, so a new word fails until an example shows it. Sixteen examples: nine market-side, six sending, and `loopback-tour`, which plays both sides; `tests/test_scenario_sending.py::test_the_whole_language_is_covered` holds the set to every verb, block kind, statement shape and context name. Every sending example runs on `LOOP-CLI` (`store.LOOPBACK`), which `setup_loopback` creates.

## Running: `runner.py`, `instance.py`, `clock.py`

`ScenarioRunner(engine, clock=None)` subscribes to `engine.events` **only while a run is armed** and acts through `engine.perform(op, payload, source="scenario")`. `arm(scenario, session=, seed=, speed=) -> Run`; `stop`, `pause`/`resume`, `detach(order_key)`, `settle()`. `on_change(instance)` and `on_log(run, instance, line, text)` are the hooks the storage layer will hang on; until then runs, instances and their logs live in memory (`Run.instances`, `Run.log`, `Run.verdict`, `Run.counts()`).

- **Sending: `run [on SESSION]`.** `arm` starts these blocks at once, on `Run.session_of(block)`: the run's session when one was given (it wins over the one written), else the block's; neither is a `ScenarioError`. A block with `new` among its own lines is one order's script. Otherwise the block is a *generator* (an `Instance` with `generator=True` and no order, kept in `Run.generators`, never mirrored to the tables): it runs the lines around the `repeat` that holds the `new` — the checker refuses actions, waits and `when` there — and each pass of that `repeat` calls `_start_script`, a new `Instance` with the pass's `n` and a copy of the names, paced by `at`/`every` and not waited on. A sending script has `order is None` until `new`: a second `new`, or any other action first, is a `ScriptError`. `replace`/`cancel` take the order's last accepted terms (`Instance._as_entered`, what the dialogs prefill) under the script's own, and name `orig_cl_ord_id` = the current ClOrdID. A run with only `run on` blocks ends itself (`finished`, `on_run_finished`) when its last script does.
- **Claiming a sent order.** `send_new_order` emits `sent order` *after its row is written and before the send* — an acknowledgement handled inside the send must find an owner — carrying `source` and the script's `tag` (`"<run>:<index>"`, passed as `_tag` through `perform`). The runner binds the order to `_claims[tag]` there; if nobody was listening, `_act` binds after `perform` returns. `perform`'s own event for `send_new_order` is a plain `action`.
- **Attached: `on sent order`.** A `sent order` whose source is not `scenario` — sent by hand, or a row an ExecutionReport created (Message Replay) — is offered to the armed `attached` blocks exactly as received orders are to `market` blocks. An order a script sent is never offered.
- **Ownership.** A received `order` event from the wire is offered to the armed runs in arming order, each run's `on order` blocks in script order; the first `where` that is true owns it (`owners[fix_orders.id]`), and an order has one owner. Orders that existed before arming are never taken. `where` sees the order's columns as names plus `order`. A failing `where` is logged and counts as false.
- **Routing.** Later events reach the owner by `order_key`: wire events as their `kinds`; an action with `source="manual"` as a `manual` event (`event.op`); the instance's own actions (`source="scenario"`) only refresh `instance.order` — a script never hears itself. `session up`/`session down` (emitted by `update_session_state` when ACTIVE-ness flips) fan out to every instance on that session.
- **Instance = one block bound to one order.** The *main flow* runs the lines; passing a `when` registers a handler that lives as long as the block it is written in (top-level ones outlive the last plain line: status `listening`). An event that some handler names spawns a flow which tries the handlers in order — the first whose guard is true runs, beside the main flow. Flows share `vars` (one flat scope; `let` on an existing name changes it) and `order`; each has its own `event`, `trade`, `since`, `n`. Actions of an instance go one at a time (`_action_lock`), and the subject — the order's current ClOrdID, or the trade target — is read under that lock.
- **Waiting.** Each instance keeps an event log; a flow's `wait`/`expect` scans from its own cursor, so an event that arrived before the `wait` started is not missed, then parks until the next delivery or its timeout (after which `event.kind` is `timeout`). A handler's flow starts its cursor after the event that spawned it.
- **Values.** `Instance.value` compiles each `Expr` once (`compile_node`, or `compile_template` when `Expr.template`), and loads `trades` (for a received order our TX executions by `order_id`; for a sent one the RX executions under any ClOrdID its row has held; busted ones included) and `history` (`fix_orders__history`) only when `field_refs` names them. Trade targets `last`/`first`/`where` consider live (not busted) trades only. `elapsed` and `since` are script seconds (wall time × speed).
- **Ends.** `completed` (ran off the end, no live `when`), `listening`, `passed`/`failed` (a verdict, a failed `expect`, a `ScriptError`), `stopped` (`stop`, or the run stopped), `detached`. A `ScriptError` names its line: a failing expression, an action the engine refused or a trade target matching nothing (both become an `error` event instead under `on error continue`), a loop that ran `RUNAWAY_LOOPS` times without once parking, more than `max_actions` actions on one order — the last two are what stops a re-notify/dispute ping-pong.
- **Pause** parks a flow before its next line (`Run._gates`); a wait already under way runs out first.
- **The engine enforces less than the buttons do.** Blotter gates such as "no Fill on a Rejected order" are `enable.when` expressions in app.json, not engine checks, so a script can do what a button would not offer. That is wanted (`misbehaving-counterparty`), and it is why the docs must not promise "exactly what a button can".

### In the database: `store.py`

`engine.scenarios` is a `ScenarioManager`: what `fix_cmd` talks to (`check_scenario`, `save_scenario`, `delete_scenario`, `scenario_vocab`, `list_examples`, `get_example`, `arm_scenario`, `run_scenario`, `stop_scenario`, `move_run`, `run_loopback_tour`, `stop_run`, `pause_run`, `resume_run`, `detach_instance`). The runner stays the authority on what is running; four tables are its shadow, written **in order by one worker** fed from the runner's synchronous hooks (`flush()` = runner settled and queue drained — tests call it after every inbound message).

- `fix_scenarios` (versioned; unique `name`; `problems` = error count at save): a Save with problems is kept as a draft, and the name a script gives itself must equal the name it is saved under. Deleting an armed scenario is refused.
- `fix_scenario_runs`: one arming — `version` (the scenario row's `_mkio_version`), `session`, `seed`, `speed`, `status` (`armed`/`paused`/`stopped`/`interrupted`), `verdict`, counters. `fix_scenario_instances` (unique `(run_id, order_row)`; upserted on status/line/wait changes) and `fix_scenario_log`. All three are archive group `data`; an online archive touching orders, trades or these tables is refused while a run is armed (`check_archive`).
- Taking an order writes `fix_orders.scenario` = `"<name> #<run id>"` (op `tag_order`; outside ORDER_COLS/ORDER_UPDATE_COLS, so no order write touches it).
- `setup_loopback(port=9880)` creates `LOOP-MKT` (acceptor) and `LOOP-CLI` (initiator on 127.0.0.1) if missing and starts them, acceptor first; an existing pair keeps its port. Found with it, running the tour over real TCP at 20×: the engine's automatic reject of a request naming no order now carries CxlRejReason(102)=1, so the requester keeps its own status instead of taking the reject's 39=8.
- **Restart.** `stop()` says nothing to the tables, so runs stay `armed`. `start()` (from `FixEngine.start`, after sessions load) marks every live run and live instance `interrupted`, then arms each of those scenarios again as a fresh run with the same session, seed and speed — unless the script no longer checks clean (logged), or has a `run` block: waiting again is harmless, **sending again because the server restarted is not**.
- **Record first, start second.** `arm` calls `runner.arm(start=False)`, writes and registers the run's row, *then* `runner.start(run)`. A script can fail in its first instant (`new` on a session that just dropped) and a sending-only run then ends at once; started first, the hooks found no row for the run and dropped the failure, its log line and the run's end, leaving a row that said `armed` for ever and a Stop that answered "not live" (found in use, 2026-09-20). For the same reason `runner.arm` refuses a `run` whose session is not active, `stop_run` never errors on a run that is over — it writes the row to the run's true state, or `interrupted` for a row this process never armed — and a script that ends without ever getting an order is still a row (`order_row = -1 - index`).
- `arm(name, side=, session=, …)` checks the script against the templates and sessions that exist and refuses errors, an unknown session and a script of the other side (`arm_scenario` passes `market`, `run_scenario` `client`). See **Sides and many runs**.

### Sides and many runs (0.49)

- **One side per script.** `vocab.side_of(kind)`: `market` blocks make a market scenario, `client` and `attached` blocks a client one (`Scenario.side`, the first block's). `check(text, side=)` reports every block of the other side — `side` is the pane the script is edited in; without it the first block decides. The UI is two of everything (Client and Market menus; `<side>-scenarios`/`-runs`/`-scripts`/`-log` panes), all over the same four tables, each stamped with `side` and each pane filtering on it; `_backfill_sides` stamps pre-0.49 rows at startup (a run whose script is gone counts as market). Names are one namespace: `save` refuses a name the other side holds, since runs, the log and an order's Scenario column name a script by name alone.
- **Any number of live runs**, of one script or many. The only refusal is a run that could never be given an order: a script with no `run` block, armed again for the same session filter. Delete is refused while any run is live; an edit is not — a `Run` holds its parsed `Scenario`, and the editor marks live lines only for runs of the saved version. `stop_scenario(name)` stops every live run of a script (the editor's Stop all); `runner.max_live` (20,000) caps live scripts across all runs, beside the per-run `max_instances`.
- **Priority.** `runner.runs` order is offer order. `Run.waits` = it has `on` blocks; `runner.offered(side)` lists those, `runner.move(run, up)` swaps neighbours of one side, and `store._renumber` mirrors each waiting run's 1-based place into `fix_scenario_runs.priority` (0 = only sends, or over) after every arm, stop and `move_run`. `_recover` re-arms by `priority`, so the line survives a restart; a scenario with a `run` block is still never run again.
- **The tour.** `TOUR` = `loopback-venue` (market) + `loopback-client` (client); `run_tour` (`fix_cmd run_loopback_tour`, the Examples page's button) sets up the sessions, waits for `LOOP-CLI` to log on, saves the two examples unless scripts of those names exist, arms the venue on `LOOP-MKT` unless already armed, and runs the client on `LOOP-CLI`. Examples name no session (`test_scenario_ui` enforces it); a client example's `Needs:` says `LOOP-CLI`.

### Time and quiescence: `clock.py`

A flow is parked only in `_sleep`, `_wait` and `_gate`. `Scheduler` keeps the *set* of busy flows: `wake(flow, future, value)` marks the flow busy before resolving its future, parking and ending clear it, and both are idempotent — which is what makes cancelling a flow at any point safe. `settle()` returns when no flow is busy; busy includes awaiting a real database commit inside `perform`. `VirtualClock.advance(seconds)` fires due timers one at a time, settling after each, so tests run minutes of script in the time their writes take and are deterministic (`seed` drives `RANDOM()` and jitter through a per-instance `random.Random(f"{seed}:{index}")`). Tests follow every inbound message with `await runner.settle()`.

## Rules the examples fixed

- A script with live top-level `when` lines stays alive after its last plain line has run, until `stop`, a verdict, or the end of the run: `cancel-replace-desk` refuses a too-late cancel after the order has filled, `dispute-desk` answers disputes after its only fill.
- For one event the first matching `when` wins; handlers run beside the main flow; an instance's actions go one at a time.
- A re-notified fill is a new trade (the engine infers nothing); `event.prev` is how a script tells it from a fill that moved CumQty.
