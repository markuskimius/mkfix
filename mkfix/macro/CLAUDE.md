# mkfix/macro — the macro language

**Naming.** Through 0.50 these were *scenarios*, and each order's running copy a *script*; 0.51 renamed everything — the package, tables (`fix_macros`, `fix_macro_runs`, `fix_macro_orders` — once `…_instances` — `fix_macro_log`, `fix_orders.macro`), services, `fix_cmd` commands, pane ids, UI files, CSS (`macro-`), archive aliases. Nothing was migrated: `upgrade.retire_scenarios` drops the old tables and column at startup and `strip_retired` leaves them out of an old archive on restore. In code an order's running copy is still an `Instance`; in everything a user reads it is "an order's macro", and the pane listing them is Macro Orders.

A small language for acting on orders as events arrive. This directory holds the language — words, parser, checker, bundled examples — and what runs it: the interpreter, the runner and their clock. All three kinds of block run. The engine side it all stands on is in `../fix/CLAUDE.md`.

`check(text, templates=None, sessions=None) -> (Macro, [Diagnostic])` is the way in. It never raises on a bad macro: every problem comes back as a `Diagnostic(line, col, end, message, severity)` — lines from 1, columns from 0 — which is what the editor underlines. `errors(diagnostics)` are the ones that stop a macro being armed or run; a `warning` does not.

## Shape of a macro

Optional `seed N` and `on error continue`, then blocks. The text carries no name: a macro is named where it is saved (`Macro.name` is set by `_armable` from the row), so the file, the editor's New and Import, and the recorder never write one. Through 0.54 every macro opened with `macro NAME`; the parser now refuses that line by name, and `upgrade.retire_macro_lines` strips it from saved rows at startup. Blocks by indentation (spaces only), one statement per line, `#` comments. Three kinds of block, `Block.kind`:

| Header | kind | The order is |
|---|---|---|
| `on order [where EXPR]` | `market` | one we received; verbs accept, reject, fill, unsol cxl, restate, correct, bust, renotify |
| `run [on SESSION]` | `client` | one the macro sends with `new`; verbs new, replace, cancel, dk. Without `on SESSION` the session is chosen at Run… (`Macro.needs_session`) |
| `on sent order [where EXPR]` | `attached` | one sent some other way (by hand, Message Replay); client verbs except `new` |

One order per macro instance. Everything that computes a value is an mkio expression (language 2: `and or not in`, durations as seconds), evaluated in `functions.ENV` — the defaults plus the opt-in `macro` library (`TICK`, seeded `RANDOM`), which app.json's expressions can never see.

## Files

- `vocab.py` — **the single source of words**: `VERBS` (name → engine op, sides, terms → payload keys, required terms, whether it takes a trade target), `EVENTS` (sides, whether it carries a trade), `STATEMENTS` (form + help), `ENUMS` (bare words for side/type/tif/handl_inst/reasons → FIX codes; held to app.json's dialog options by a test), and the schemas `check_fields` checks expressions against (`scope_schema`, `match_schema` — order and trade fields are read from `mkfix.toml`'s table columns, so a new column is known at once). `vocabulary()` is all of it as plain data, help text included, for the editor and the reference pages. Nothing else may list these words.
- `parser.py` — lines → `nodes`. A `_Line` cursor takes words and phrases; expressions are parsed **in place, on the line's own text**, with `expr.parse_prefix`, which ends at a comma, one of our keywords, `±`, or the `#` of a comment — so an expression cannot run onto the next line and node positions are columns. `wait … where EXPR or timeout D` passes `stop=("or timeout",)`; the `+/-` spelling of jitter is fenced off with `until`. A bad line is reported and skipped, a bad compound line takes its body with it, and parsing goes on: the editor shows every problem at once.
- `check.py` — meaning: verb and event against the block's side, terms against the verb, required terms (unless `using` a template), trade targets (a trade verb needs `last trade` / `first trade` / `trade where …` unless it sits under a `when` whose events all carry a trade), every expression compiled and its field paths checked, `${…}` inside quoted values checked as templates (`Expr.template`), templates and sessions when the caller knows them. `let` and `with` names are known block-wide — a macro has one flat scope per order, and `let` on a name that exists changes it.
- `nodes.py` — the tree; `walk(body)` and `expressions(statement)` are how everything else traverses it.
- `examples/*.macro` — shipped in the wheel, read-only, opened as copies. Each opens with `# Title`, a bare `#`, then `Shows` / `Needs` / `Watch` / `Outcome` lines the Help page will be built from. They are the acceptance set: `tests/test_macro.py` requires each to check clean and the set to use every market-side verb, event, statement, trade target, context name and both macro functions, so a new word fails until an example shows it. Sixteen examples: nine market-side, six sending, and `loopback-tour`, which plays both sides; `tests/test_macro_sending.py::test_the_whole_language_is_covered` holds the set to every verb, block kind, statement shape and context name. Every sending example runs on `LOOP-CLI` (`store.LOOPBACK`), which `setup_loopback` creates.

## Running: `runner.py`, `instance.py`, `clock.py`

`MacroRunner(engine, clock=None)` subscribes to `engine.events` **only while a run is armed** and acts through `engine.perform(op, payload, source="macro")`. `arm(macro, session=, seed=, speed=) -> Run`; `stop`, `pause`/`resume`, `detach(order_key)`, `settle()`. `on_change(instance)` and `on_log(run, instance, line, text)` are the hooks the storage layer will hang on; until then runs, instances and their logs live in memory (`Run.instances`, `Run.log`, `Run.verdict`, `Run.counts()`).

- **Sending: `run [on SESSION]`.** `arm` starts these blocks at once, on `Run.session_of(block)`: the run's session when one was given (it wins over the one written), else the block's; neither is a `MacroError`. A block with `new` among its own lines is one order's macro. Otherwise the block is a *generator* (an `Instance` with `generator=True` and no order, kept in `Run.generators`, never mirrored to the tables): it runs the lines around the `repeat` that holds the `new` — the checker refuses actions, waits and `when` there — and each pass of that `repeat` calls `_start_script`, a new `Instance` with the pass's `n` and a copy of the names, paced by `at`/`every` and not waited on. A sending macro has `order is None` until `new`: a second `new`, or any other action first, is a `ScriptError`. `replace`/`cancel` take the order's last accepted terms (`Instance._as_entered`, what the dialogs prefill) under the macro's own, and name `orig_cl_ord_id` = the current ClOrdID. A run with only `run on` blocks ends itself (`finished`, `on_run_finished`) when its last macro does.
- **Claiming a sent order.** `send_new_order` emits `sent order` *after its row is written and before the send* — an acknowledgement handled inside the send must find an owner — carrying `source` and the macro's `tag` (`"<run>:<index>"`, passed as `_tag` through `perform`). The runner binds the order to `_claims[tag]` there; if nobody was listening, `_act` binds after `perform` returns. `perform`'s own event for `send_new_order` is a plain `action`.
- **Attached: `on sent order`.** A `sent order` whose source is not `macro` — sent by hand, or a row an ExecutionReport created (Message Replay) — is offered to the armed `attached` blocks exactly as received orders are to `market` blocks. An order a macro sent is never offered.
- **Ownership.** A received `order` event from the wire is offered to the armed runs in arming order, each run's `on order` blocks in macro order; the first `where` that is true owns it (`owners[fix_orders.id]`), and an order has one owner. Orders that existed before arming are never taken. `where` sees the order's columns as names plus `order`. A failing `where` is logged and counts as false.
- **Routing.** Later events reach the owner by `order_key`: wire events as their `kinds`; an action with `source="manual"` as a `manual` event (`event.op`); the instance's own actions (`source="macro"`) only refresh `instance.order` — a macro never hears itself. `session up`/`session down` (emitted by `update_session_state` when ACTIVE-ness flips) fan out to every instance on that session.
- **Instance = one block bound to one order.** The *main flow* runs the lines; passing a `when` registers a handler that lives as long as the block it is written in (top-level ones outlive the last plain line: status `listening`). An event that some handler names spawns a flow which tries the handlers in order — the first whose guard is true runs, beside the main flow. Flows share `vars` (one flat scope; `let` on an existing name changes it) and `order`; each has its own `event`, `trade`, `since`, `n`. Actions of an instance go one at a time (`_action_lock`), and the subject — the order's current ClOrdID, or the trade target — is read under that lock.
- **Waiting.** Each instance keeps an event log; a flow's `wait`/`expect` scans from its own cursor, so an event that arrived before the `wait` started is not missed, then parks until the next delivery or its timeout (after which `event.kind` is `timeout`). A handler's flow starts its cursor after the event that spawned it.
- **Values.** `Instance.value` compiles each `Expr` once (`compile_node`, or `compile_template` when `Expr.template`), and loads `trades` (for a received order our TX executions by `order_id`; for a sent one the RX executions under any ClOrdID its row has held; busted ones included) and `history` (`fix_orders__history`) only when `field_refs` names them. Trade targets `last`/`first`/`where` consider live (not busted) trades only. `elapsed` and `since` are macro seconds (wall time × speed).
- **Ends.** `completed` (ran off the end, no live `when`), `listening`, `passed`/`failed` (a verdict, a failed `expect`, a `ScriptError`), `stopped` (`stop`, or the run stopped), `detached`. A `ScriptError` names its line: a failing expression, an action the engine refused or a trade target matching nothing (both become an `error` event instead under `on error continue`), a loop that ran `RUNAWAY_LOOPS` times without once parking, more than `max_actions` actions on one order — the last two are what stops a re-notify/dispute ping-pong.
- **Pause** parks a flow before its next line (`Run._gates`); a wait already under way runs out first.
- **The engine enforces less than the buttons do.** Blotter gates such as "no Fill on a Rejected order" are `enable.when` expressions in app.json, not engine checks, so a macro can do what a button would not offer. That is wanted (`misbehaving-counterparty`), and it is why the docs must not promise "exactly what a button can".

### In the database: `store.py`

`engine.macros` is a `MacroManager`: what `fix_cmd` talks to (`check_macro`, `save_macro`, `delete_macro`, `macro_vocab`, `list_examples`, `get_example`, `arm_macro`, `run_macro`, `stop_macro`, `move_run`, `run_loopback_tour`, `stop_run`, `pause_run`, `resume_run`, `detach_order`). The runner stays the authority on what is running; four tables are its shadow, written **in order by one worker** fed from the runner's synchronous hooks (`flush()` = runner settled and queue drained — tests call it after every inbound message).

- `fix_macros` (versioned; unique `name`; `problems` = error count at save): a Save with problems is kept as a draft, and the name a macro gives itself must equal the name it is saved under. Deleting an armed macro is refused.
- `fix_macro_runs`: one arming — `version` (the macro row's `_mkio_version`), `session`, `seed`, `speed`, `status` (`armed`/`paused`/`stopped`/`interrupted`), `verdict`, counters. `fix_macro_orders` (unique `(run_id, order_row)`; upserted on status/line/wait changes) and `fix_macro_log`. All three are archive group `data`; an online archive touching orders, trades or these tables is refused while a run is armed (`check_archive`).
- Taking an order writes `fix_orders.macro` = `"<name> #<run id>"` (op `tag_order`; outside ORDER_COLS/ORDER_UPDATE_COLS, so no order write touches it).
- `setup_loopback(port=9880)` creates `LOOP-MKT` (acceptor) and `LOOP-CLI` (initiator on 127.0.0.1) if missing and starts them, acceptor first; an existing pair keeps its port. Found with it, running the tour over real TCP at 20×: the engine's automatic reject of a request naming no order now carries CxlRejReason(102)=1, so the requester keeps its own status instead of taking the reject's 39=8.
- **Restart.** `stop()` says nothing to the tables, so runs stay `armed`. `start()` (from `FixEngine.start`, after sessions load) marks every live run and live instance `interrupted` and plays **nothing** again (`_recover`). Through 0.50 a waiting-only macro was re-armed as a fresh run in its old priority; with Play/Stop on the blotters the user saw ▶ lit after a restart and called it a bug — a run is something a person started. Sending macros were never run again: **a restart never sends anything**.
- **Record first, start second.** `arm` calls `runner.arm(start=False)`, writes and registers the run's row, *then* `runner.start(run)`. A macro can fail in its first instant (`new` on a session that just dropped) and a sending-only run then ends at once; started first, the hooks found no row for the run and dropped the failure, its log line and the run's end, leaving a row that said `armed` for ever and a Stop that answered "not live" (found in use, 2026-09-20). For the same reason `runner.arm` refuses a `run` whose session is not active, `stop_run` never errors on a run that is over — it writes the row to the run's true state, or `interrupted` for a row this process never armed — and a macro that ends without ever getting an order is still a row (`order_row = -1 - index`).
- `arm(name, side=, session=, …)` checks the macro against the templates and sessions that exist and refuses errors, an unknown session and a macro of the other side (`arm_macro` passes `market`, `run_macro` `client`). See **Sides and many runs**.

### Sides and many runs (0.49)

- **One side per macro.** `vocab.side_of(kind)`: `market` blocks make a market macro, `client` and `attached` blocks a client one (`Macro.side`, the first block's). `check(text, side=)` reports every block of the other side — `side` is the pane the macro is edited in; without it the first block decides. The UI is two of everything (Client and Market menus; `<side>-macros`/`-runs`/`-macros`/`-log` panes), all over the same four tables, each stamped with `side` and each pane filtering on it; `_backfill_sides` stamps pre-0.49 rows at startup (a run whose macro is gone counts as market). Names are one namespace: `save` refuses a name the other side holds, since runs, the log and an order's Macro column name a macro by name alone.
- **Any number of live runs**, of one macro or many. The only refusal is a run that could never be given an order: a macro with no `run` block, armed again for the same session filter. Delete is refused while any run is live; an edit is not — a `Run` holds its parsed `Macro`, and the editor marks live lines only for runs of the saved version. `stop_macro(name)` stops every live run of a macro (the editor's Stop all); `runner.max_live` (20,000) caps live macros across all runs, beside the per-run `max_instances`.
- **Priority.** `runner.runs` order is offer order. `Run.waits` = it has `on` blocks; `runner.offered(side)` lists those, `runner.move(run, up)` swaps neighbours of one side, and `store._renumber` mirrors each waiting run's 1-based place into `fix_macro_runs.priority` (0 = only sends, or over) after every arm, stop and `move_run`. A restart clears the line with the runs (`_recover`).
- **The tour.** `TOUR` = `loopback-venue` (market) + `loopback-client` (client); `run_tour` (`fix_cmd run_loopback_tour`, the Examples page's button) sets up the sessions, waits for `LOOP-CLI` to log on, saves the two examples unless macros of those names exist, arms the venue on `LOOP-MKT` unless already armed, and runs the client on `LOOP-CLI`. Examples name no session (`test_macro_ui` enforces it); a client example's `Needs:` says `LOOP-CLI`.

### Recording: `recorder.py`

`Recorder(engine, side, session="", clock=time.monotonic)` subscribes to `engine.events` while it records (so the bus is live and `perform` announces actions) and keeps a timeline per order: `heard` steps (wire events a macro could wait for — `cancel`/`replace`/`dk` on the market side, the client events bar `er`/`message`; `filled` wins over `fill`) and `did` steps (manual `action` events; `_VERB_OF` maps every `ACTIONS` op to its verb — tested to be total). A market order is followed from its wire `order` event, a client order from a manual `sent order`; one already under way, one with a `macro` tag, or the wrong `direction` is ignored. `perform`'s event carries `detail.data` (the payload without `_` keys) and `detail.trade_before` for this: a correction is named by the terms the trade had. `stop(name, delays=)` writes the text, **event-triggered** (0.52, the user's call): every `heard` since the last action is written in order — `expect E within max(5 s, 3× the gap)` on the client side, `wait E` on the market side (a trailing wait nothing follows is dropped) — and the action follows with no delay; a market order's arrival counts as heard, so its first action has none; `after DELAY` appears only between two actions with nothing heard between them (under 50 ms dropped, the rest rounded by `_duration`). Market side, `_handlers`: a request kind (`cancel`/`replace`/`dk`) whose every occurrence was answered by the next step with the same verb and terms (`_ANSWERS`) leaves the main flow and becomes a top-of-block `when E` / answer — top-level handlers outlive the main flow (`listening`) — with `stop` after an accepted cancel that nothing was done after; one answered two ways, or left unanswered once, stays sequential. `delays=True` (the Stop dialog's and the editor prompt's "Keep my delays"; the timeline holds the timing either way) adds the think time: `after` between wait and action, and leading a handler's answer; `replace` keeps only the terms that differ from `prev`; codes become enum words; a client timeline that ends on something heard ends `pass`; trade targets resolve at stop against the order's trades stamped no later than the action. Market timelines with the same statements (delays aside) share a block (`symbol in […]`); a symbol in two groups gets `and order_qty == …`, narrower blocks first; client orders are one `run` block each, later ones led by `after OFFSET`. The output always checks clean (`test_macro_recorder.py` runs recordings against each other). `MacroManager.record_start/record_stop/record_status` hold one recorder a side (`fix_cmd` commands of the same names); `stop()` ends them unwritten.

### The order blotters' controls (0.51)

`play(side, what, …)` — one choice or several joined by commas (the dialog's checklist): `macro:NAME`/`needs:NAME` arms/runs it, `resume:ID|all` resumes that side's paused runs; every choice is checked first (`_armable` + `runner.validate`, the refusals of `arm` without its effects), so a list is played whole or not at all, and one session, speed and seed serve all; `pause_runs(side, run="")` and `stop_runs(side, run="")` take one run by row id or the whole side (`_side_runs` refuses a run of the other side or in the wrong state); `record_stop(side, name, save=True)` checks the name is free *before* stopping (a clash leaves it recording), saves only when something was recorded, and answers `saved`; `status()` is both sides' recordings for the UI's poll (`fix_cmd` `play_macro`, `pause_runs`, `stop_runs`, `macro_status`). `fix_macros.needs_session` is written at save so the Play… dialog can require a session only where the macro names none.

### Time and quiescence: `clock.py`

A flow is parked only in `_sleep`, `_wait` and `_gate`. `Scheduler` keeps the *set* of busy flows: `wake(flow, future, value)` marks the flow busy before resolving its future, parking and ending clear it, and both are idempotent — which is what makes cancelling a flow at any point safe. `settle()` returns when no flow is busy; busy includes awaiting a real database commit inside `perform`. `VirtualClock.advance(seconds)` fires due timers one at a time, settling after each, so tests run minutes of macro in the time their writes take and are deterministic (`seed` drives `RANDOM()` and jitter through a per-instance `random.Random(f"{seed}:{index}")`). Tests follow every inbound message with `await runner.settle()`.

## Rules the examples fixed

- A macro with live top-level `when` lines stays alive after its last plain line has run, until `stop`, a verdict, or the end of the run: `cancel-replace-desk` refuses a too-late cancel after the order has filled, `dispute-desk` answers disputes after its only fill.
- For one event the first matching `when` wins; handlers run beside the main flow; an instance's actions go one at a time.
- A re-notified fill is a new trade (the engine infers nothing); `event.prev` is how a macro tells it from a fill that moved CumQty.
