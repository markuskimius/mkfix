# mkfix/macro — the macro language

**Naming.** Through 0.50 these were *scenarios*; 0.51 renamed everything with no migration (`upgrade.retire_scenarios` drops the old tables and column at startup, `strip_retired` leaves them out of an old archive on restore). In code an order's running copy is an `Instance`; in everything a user reads it is "an order's macro", a row under a run in the Macro Runs window.

A small language for acting on orders — and, since 0.64, IOIs, adverts and allocations — as events arrive. This directory holds the language — words, parser, checker, bundled examples — and what runs it: the interpreter, the runner and their clock. All three kinds of block run. The engine side it all stands on is in `../fix/CLAUDE.md`.

`check(text, templates=None, sessions=None) -> (Macro, [Diagnostic])` is the way in. It never raises on a bad macro: every problem comes back as a `Diagnostic(line, col, end, message, severity)` — lines from 1, columns from 0 — which is what the editor underlines. `errors(diagnostics)` are the ones that stop a macro being armed or run; a `warning` does not.

## Shape of a macro

Optional `seed N` and `on error continue`, then blocks. The text carries no name: a macro is named where it is saved (`Macro.name` is set by `_armable` from the row), so the file, the editor's New and Import, and the recorder never write one. Through 0.54 every macro opened with `macro NAME`; the parser now refuses that line by name, and `upgrade.retire_macro_lines` strips it from saved rows at startup. The name rule is `store.NAME` (letters, digits, spaces, `. _ - :`, leading alphanumeric): a comma is out because Play…'s checklist joins its choices with commas (`macro:NAME`, split at the first colon, so colons in names are fine), and Export (`exportFileName` in macro-lang.js) writes a colon as a dot in `<name>.macro`. Stop suggests `recordingName(side)` — `Market 2026-09-22 14:30:15`, local time — and the recorder's header comment names the side, so a renamed file still says which editor it belongs in. Blocks by indentation (spaces only), one statement per line, `#` comments. Three kinds of block, `Block.kind`:

| Header | kind | The subject is |
|---|---|---|
| `on order [where EXPR]` | `market` | an order we received; verbs accept, reject, fill, unsol cxl, restate, correct, bust, renotify |
| `run [on SESSION]` | `client` | one the macro sends: an order with `new` (verbs new, replace, cancel, dk), or an IOI/advert/allocation with `ioi`/`advert`/`allocate` (their `replace …`/`cancel …`). Without `on SESSION` the session is chosen at Run… (`Macro.needs_session`) |
| `on sent order [where EXPR]` | `attached` | an order sent some other way (by hand, Message Replay); client verbs except `new` |
| `on ioi` / `on advert` / `on allocation [where EXPR]` | `market` | one we received; `new` answers an IOI (tag 23, an order nobody's macro owns), `accept allocation`/`reject allocation` answer an allocation |
| `on sent ioi` / `on sent advert` / `on sent allocation [where EXPR]` | `attached` | one sent by hand; `replace …`/`cancel …` |

**Subjects (0.64).** `Block.subject` ∈ `vocab.SUBJECTS` (`order`, `ioi`, `advert`, `allocation`; `SUBJECT_TABLES`/`SUBJECT_IDS` name the table and ID column, `CREATORS` the sending verb); the parser sets a `run` block's from the first sending verb in it (`_CREATOR_SUBJECT`), the header decides the rest (`BLOCK_HEADERS`). The side turns with the subject: `side_of(kind, subject)` — the market side receives orders and sends the three families, the client side the other way round — so `on ioi` is a client block and a `run` with `ioi` a market one. A verb or event stands where its `places` (`(subject, kind)` pairs: `subject` + `sides`, plus `also`) allow; the checker names blocks with `block_name`. Words for a term depend on the verb (`_ENUM_OF`, `enum_of(verb, term)`: `side` on `ioi` is `ioi side`, on `advert` `adv side`; `quality`, `natural`, `alloc type`, `alloc status`, `alloc reject reason`). Expressions see the subject's row under its own name (`scope_schema(names, subject)`, `SUBJECT_FIELDS`; `event.prev` is that row too; `trades` only for orders; `history` from the subject's `__history` table); `order` is absent in an IOI block.

**RFQs (0.73).** Three more subjects:
- `rfq` and `quote` share fix_rfqs, and `vocab.subject_of_row` reads which one a row is from its `origin`. `rfq_request` has fix_rfq_requests.
- `SUBJECT_WORDS` is how a subject is written in headers and at the head of the engine's events. `rfq_request` is `rfq request`, so the runner, recorder and `_macro_kinds` strip `rfq request `.
- `CLIENT_SENDS` = order and rfq: the client sends RFQs as it sends orders, so `on rfq` is a market block and `on quote`/`on rfq request` client ones.
- Creators: `rfq`, `new quote`, `rfq request`.
- `Verb.key` names the row column a verb's payload carries: `quote_id` for `hit`/`counter`/`pass quote`/`requote`/`cancel quote` (on either subject), `quote_req_id` for `quote`/`reject rfq`, `rfq_req_id` for `unsubscribe`.
- `ANSWER_TAGS` generalizes the IOI rule. `new` in an ioi, quote or rfq block adds 23 or 117; `rfq` in an `on rfq request` block adds 644. What it sends belongs to no macro.
- `quote`, `requote` and `counter` fill in the standing quote's prices, sizes and type under the macro's own terms (`Instance._quote_as_entered`); a fresh RFQ's sizes default to the size asked.
- `pass quote` is a verb. The parser checks `at_phrase("pass quote")` before the `pass` verdict, and macro-lang.js colours verbs before statements.
- Events: `quoted`, `requoted`, `status`, `hit`, `countered`, `passed`, `response`, `unsubscribed`, `answered`; `canceled`, `rejected` and `expired` gained RFQ places.
- Recorder: `_creator_terms` covers the new subjects, `_SYMBOL_COL` (an RFQ request's `symbols`), and a `countered` answered the same way every time becomes a `when` rule.
- history.py: `_negotiation` walks R/S/Z/AG/AI/AJ/D by 131 and the chain's 117s. A stream opens on its first QuoteID. `_rfq_request` walks AH and the Rs naming 644.
- Examples: seven, in `examples/CLAUDE.md`.

**Lists (0.78).** Subject `list` (fix_lists, `list_id`), sent by the client (`CLIENT_SENDS`): creator `new list`, headers `on list` (market) and `on sent list`; `lists` is the run's rows.
- `new list` is the one verb with a body (`Action.body`), holding `order` lines (`OrderLine`: `new`'s terms, checked by `check.order_line` as a pseudo `new`, refused outside `new list`); a block under an `order` line, or under `add order`, is that order's own macro (`nodes.member_macros`; checked as an `ATTACHED` order block). `walk` goes into `new list`'s body, not the orders' blocks.
- `Instance._new_list`: `mode: list` (E) collects the lines' terms and sends one `send_new_list` at the end, then starts each member macro on its row (`engine._list_members`, zipped in order); `mode: orders` (D) sends the first line as `send_new_list` and each later one as `add_list_order` as reached, so `after`/`repeat` pace it, `tot_orders: N` riding as 68=N on every order (`actions._count` → `tot_count`). `_list_send` is `_act`'s lock/count/error path; `_terms` is shared by `_act` and the lines. `runner._start_member` makes the order's `Instance` (block `ATTACHED`/`ORDER`, the list macro's names copied) and binds it.
- The list's orders carry its tag (`_tag`, and `detail.tag` on send_new_list's `sent order` events), so they are neither claimed nor offered to `on sent order` blocks.
- Received: `on list` blocks are offered at `received` (the runner's `_on_event`), not at the list's first order. A NewOrderList emits `list received` itself; a D-mode list's `list`/`list joined` (re)start `runner._list_quiet`, a timer of `vocab.LIST_QUIET` (5 s) macro time at the fastest armed run's speed (`clock.call_later` on a token the scheduler counts), which emits `list received`; later orders are `joined`. `_cancel_quiet` on `stop_all`.
- Events: `accepted`/`rejected`/`executing`/`status` (ListStatus), `done` (the last sent order finished), `joined`, `execute`, `status request` (answered by the engine from the tables before the macro hears it), `cancel`.
- Recorder: a sent list's recorded orders become its `order` lines (members matched by `list_id`, in `list_seq_no` order, and folded out of the top level), those an `add order` step sent its block (`_Timeline.children`); a received list is `on list where order_count == N`. history.py writes lists too (0.80, `_list`): see RECORDING.md.
- Examples: `list-trader`, `list-desk`, `drip-basket`. `tests/test_macro_lists.py`.
- `rfq request` takes `instruments: 'A, B'` (0.80): declared or saved names, resolved by the instance into terms (`instruments_named` checks literal ones); the recorder writes them by name and declares them (`_rfq_instruments`, `_declare`). `Instance._taken_over`: a quote macro whose action is refused because another `new quote` already took its row is detached, not failed.

**Multileg (0.79).** `new multileg` is a second sender of orders (`vocab.SENDERS`, which the parser, checker, instance and runner consult instead of `CREATORS`): the strategy's terms, `leg` lines under it (`LegLine`, `LEG_TERMS`), or `instrument: 'NAME'` naming a strategy (`_strategy` → `runner._strategy`: a declared `instrument` with `leg` lines — literal, no nested `instrument` — or one saved with legs; `instrument_payload` carries `legs`). `replace` takes `leg` lines too (an AC). `nodes.LEGGED` verbs' bodies are their legs (`walk` yields them); `check.legs`/`leg_line`/`strategy_named`/`not_a_strategy`. `fill` gains `leg` (price then not required) and `report_legs` (`report legs` enum, Y). `event.leg` (`''` for the order's own), `legs` context (`runner._legs`, `LEG_FIELDS`). Recorder: a sent multileg order is `new multileg` + `leg` lines as it went out (the AB's legs, snapshotted at birth as `_legs`), or `instrument: 'NAME'` and a declaration when the legs are a saved strategy's (`_legs_key`); a replace with legs writes them under it (`_Step.legs`). history.py reads AB/AC and leg reports (`fill leg: N`). Examples `calendar-spread`, `spread-desk`. Also fixed: a task cancelled before its first step (a `when` woken by the event that ended the macro) never entered `_guarded`; `_spawn`'s done callback closes its coroutine and marks the flow finished, or `settle` hung. `tests/test_macro_multileg.py`.
- Tests: `tests/test_macro_rfqs.py` plays them against each other on FIX 4.4.

**Instruments (0.75).** `new` takes an order's instrument (`vocab._INSTRUMENT_TERMS`/`_POSITION_TERMS`: `sec_type`, `maturity`, `strike`, `put_call`, `cfi`, `underlying`/`underlying_type`/`underlying_maturity`, `multiplier`, `exchange`, `security_id`/`id_source`, and the order's `open_close`/`covered`; words in ENUMS `sec type`, `put call`, `open close`, `covered`, `id source`, held to the New dialog). `replace` takes none: a replace cannot change them. `instrument: 'NAME'` (payload key `_instrument`) is resolved by `Instance._act` through `runner._instrument` — the macro's own `instrument 'NAME' …` line (`nodes.Instrument`, top level before the blocks, `Macro.instruments`, terms `DECLARED_TERMS`, literals only, a symbol required; `check.declared_payload`), else the fix_instruments row (`check.instrument_payload`) — between a `using` template and the terms written out, which override it; it brings the symbol `new` requires. The checker knows the saved ones (`check(…, instruments=)`, `MacroManager.known`): an unknown literal name is an error, a declaration differing from a saved one of its name a warning, a computed name the run's to resolve. The recorder and history write the row's instrument as terms (`recorder._instrument_terms`, words from the codes); an order whose instrument equals a saved one's (`_named`) says `instrument: 'NAME'` and the text opens with its declaration (`declarations`, joined by the end-to-end recorder too). The instrument tags are consumed, so neither writes them as extras. Since 0.76 the families' sending verbs (`ioi`, `advert`, `allocate`, `rfq`, `new quote`) take the instrument terms too, without Open/Close and Covered; their `replace …` verbs take none. `tests/test_macro_instruments.py`.

**Working together (0.68).** One subject per macro instance still, and an instance acts on its own subject only; what the instances of one *run* have to do with each other goes through the run, and never leaves it:

- `signal 'NAME' [with EXPR]` (`nodes.Signal`) → `runner._signal`: every other live instance of the run is `deliver`ed an event of kinds `("signal:NAME", "signal")` — so `when signal 'NAME'` and a bare `when signal` both match with no change to the matching — whose `kind` is plain `signal` and which carries `name`, `value`, `sender` (a copy of the sender's row, None before it has one), `subject` and `n`. A named signal stands in a statement's `events` as `vocab.signal_event(name)`; `vocab.event_of` finds its `Event`, `vocab.event_text` writes it back as `signal 'NAME'` (what a macro is `waiting_for`). The name is a quoted string read by `_QUOTED`, not an expression — one would run on into the `or` of the next event — and takes no `${…}`: what differs goes in the value. The sender never hears itself; each signal is a line of the run's log; `max_signals` (100,000 a run) stops two macros answering each other.
- `share NAME = EXPR` (`nodes.Share`) sets `Run.shared[NAME]`, read as `shared.NAME`. `runner._share` gives every name the macro sets a NULL at arm, then evaluates the top-level ones (`Macro.shares`, allowed only before the first block) in order against what is shared already; one that fails is a `MacroError` and nothing is armed.
- `orders`/`iois`/`adverts`/`allocations` (`vocab.PEERS`): `runner._peers(run, kind)` reads the rows of that kind the run's instances hold — live or done — from the table, by id, when an expression names them (as `trades` and `history` are loaded). A name of the macro's own wins: these five names are in `CONTEXT_DOCS` but not in `vocab.RESERVED`, which is what `let` and `with` refuse, so a macro written before 0.68 that calls something `orders` keeps working.
- `on signal 'NAME' [where EXPR]` is a sending block — `Block.kind` CLIENT with `Block.signal` set, its subject found as a `run`'s is — that `start` leaves alone and `_signal` starts once for every signal of that name meeting its `where` (`_started_by`: the scope is `event`, `shared` and the peers; there is no row yet). `_start_block` starts it the way `start` starts a `run` — one subject's macro, or a generator when the sending verb sits in a `repeat`, whose passes are handed the signal and the session too. The instance opens with the signal as `event`, `n` counts the block's starts (`Run._started`), and it sends on `Instance.session`: the run's session, else the session of the sender's row. `Macro.sends` and `needs_session` count `run` blocks only, so a macro of `on order` and `on signal` blocks is armed, not run, and asks for no session; `validate` checks no session for it.
- The checker knows the macro's shared names and signals macro-wide (`_Checker.shared`/`.signals`): `shared.typo` is an error, waiting for a signal nothing in the macro sends a *warning* (`heard`), since signals cannot come from outside the run. The lines around a generator's `repeat` may `share` and `signal`; they still may not wait.
- The recorder and `history.py` write none of this (`signal` is in `_NEVER_HEARD`): they write what was on the wire. `tests/test_macro_coordination.py`.

Everything that computes a value is an mkio expression (language 2: `and or not in`, durations as seconds), evaluated in `functions.ENV` — the defaults plus the opt-in `macro` library (`TICK`, seeded `RANDOM`), which app.json's expressions can never see.

## Files

- `vocab.py` — **the single source of words**: `VERBS` (name → engine op, subject, template `scope`, sides and `places`, terms → payload keys, required terms, whether it takes a trade target), `EVENTS` (subjects, sides, `places`, whether it carries a trade), `STATEMENTS` (form + help), `ENUMS` (bare words for side/type/tif/handl_inst/reasons → FIX codes; held to app.json's dialog options by a test), and the schemas `check_fields` checks expressions against (`scope_schema`, `match_schema` — order and trade fields are read from `mkfix.toml`'s table columns, so a new column is known at once). `vocabulary()` is all of it as plain data, help text included, for the editor and the reference pages. Nothing else may list these words.
- `parser.py` — lines → `nodes`. A `_Line` cursor takes words and phrases; expressions are parsed **in place, on the line's own text**, with `expr.parse_prefix`, which ends at a comma, one of our keywords, `±`, or the `#` of a comment — so an expression cannot run onto the next line and node positions are columns. `wait … where EXPR or timeout D` passes `stop=("or timeout",)`; the `+/-` spelling of jitter is fenced off with `until`. A bad line is reported and skipped, a bad compound line takes its body with it, and parsing goes on: the editor shows every problem at once.
- `check.py` — meaning: verb and event against the block's side, terms against the verb, required terms (unless `using` a template), trade targets (a trade verb needs `last trade` / `first trade` / `trade where …` unless it sits under a `when` whose events all carry a trade), every expression compiled and its field paths checked, `${…}` inside quoted values checked as templates (`Expr.template`), templates and sessions when the caller knows them. `let` and `with` names are known block-wide — a macro has one flat scope per order, and `let` on a name that exists changes it.
- `nodes.py` — the tree; `walk(body)` and `expressions(statement)` are how everything else traverses it.
- `examples/*.macro` — the bundled examples and the acceptance set: `examples/CLAUDE.md`, with the loopback pair and the tour.

## Running: `runner.py`, `instance.py`, `clock.py`

`MacroRunner(engine, clock=None)` subscribes to `engine.events` **only while a run is armed** and acts through `engine.perform(op, payload, source="macro")`. `arm(macro, session=, seed=, speed=) -> Run`; `stop`, `pause`/`resume`, `detach(order_key)`, `settle()`. `on_change(instance)` and `on_log(run, instance, line, text)` are the hooks the storage layer will hang on; until then runs, instances and their logs live in memory (`Run.instances`, `Run.log`, `Run.verdict`, `Run.counts()`).

- **Sending: `run [on SESSION]`.** `arm` starts these blocks at once, on `Run.session_of(block)`: the run's session when one was given (it wins over the one written), else the block's. A block with its sending verb (`CREATORS[block.subject]`: `new`, `ioi`, `advert`, `allocate`) among its own lines is one subject's macro. Otherwise the block is a *generator* (an `Instance` with `generator=True` and no row, kept in `Run.generators`, never mirrored to the tables): it runs the lines around the `repeat` that holds the sending verb — the checker refuses actions, waits and `when` there — and each pass of that `repeat` calls `_start_script`, a new `Instance` with the pass's `n` and a copy of the names, paced by `at`/`every` and not waited on. A sending macro has `row is None` until its verb sends: a second send, or any other action first, is a `ScriptError`. `replace`/`cancel` take the order's last accepted terms (`Instance._as_entered`, what the dialogs prefill) under the macro's own, and name `orig_cl_ord_id` = the current ClOrdID; `replace ioi`/`replace advert`/`replace allocation` likewise (`_family_as_entered`), and every family verb names the row's current ID (`subject_id`) by its `SUBJECT_IDS` key. A run with only `run on` blocks ends itself (`finished`, `on_run_finished`) when its last macro does.
- **Claiming what was sent.** `send_new_order` — and `send_ioi`/`send_advert`/`send_allocation` — emits `sent <subject>` *after its row is written and before the send* — an acknowledgement handled inside the send must find an owner — carrying `source` and the macro's `tag` (`"<run>:<index>"`, passed as `_tag` through `perform`). The runner binds the row to `_claims[tag]` there; if nobody was listening, `_act` binds after `perform` returns (`_sent_row`). `perform`'s own event for a send is a plain `action`.
- **Attached: `on sent …`.** A `sent <subject>` whose source is not `macro` — sent by hand, or a row an ExecutionReport created (Message Replay) — or that a macro sent without a tag (`new` in an `on ioi` block: an order answering the IOI, `23=<IOIID>` added to its extras unless the macro named one, belonging to no macro) is offered to the armed `attached` blocks of that subject exactly as received ones are to `market` blocks. What a macro sent and claimed is never offered.
- **Ownership.** A received `order` (`ioi`, `advert`, `allocation`) event from the wire is offered to the armed runs in arming order, each run's `on <subject>` blocks in macro order; the first `where` that is true owns it (`owners[(kind, row id)]` — the tables' ids collide, so the key is the pair; `Instance.owner_key`), and a row has one owner. Rows that existed before arming are never taken. `where` sees the row's columns as names plus the subject's name. A failing `where` is logged and counts as false.
- **Routing.** Later events reach the owner by `(kind, id)`: an order event by `ev.order`, a family event by `ev.table`/`ev.row` with the family's name dropped from its kinds (`allocation accepted` → `accepted`; `_macro_kinds`), wire events as their `kinds`; an action with `source="manual"` as a `manual` event (`event.op`); the instance's own actions (`source="macro"`) only refresh `instance.row` — a macro never hears itself. `session up`/`session down` (emitted by `update_session_state` when ACTIVE-ness flips) fan out to every instance on that session.
- **Instance = one block bound to one subject** (`kind`, `row`; `order` is the row when it is an order).
- **Waiting.** Each instance keeps an event log; a flow's `wait`/`expect` scans from its own cursor, so an event that arrived before the `wait` started is not missed, then parks until the next delivery or its timeout (after which `event.kind` is `timeout`). A handler's flow starts its cursor after the event that spawned it.
- **Values.** `Instance.value` compiles each `Expr` once (`compile_node`, or `compile_template` when `Expr.template`), and loads `trades` (the order's executions by `order_id` — TX for a received order, RX for a sent one; busted ones included) and `history` (`fix_orders__history`) only when `field_refs` names them. Trade targets `last`/`first`/`where` consider live (not busted) trades only. `elapsed` and `since` are macro seconds (wall time × speed).
- **Ends.** `completed` (ran off the end, no live `when`), `listening`, `passed`/`failed` (a verdict, a failed `expect`, a `ScriptError`), `stopped` (`stop`, or the run stopped), `detached`. A `ScriptError` names its line: a failing expression, an action the engine refused or a trade target matching nothing (both become an `error` event instead under `on error continue`), a loop that ran `RUNAWAY_LOOPS` times without once parking, more than `max_actions` actions on one order — the last two are what stops a re-notify/dispute ping-pong.
- **Pause** parks a flow before its next line (`Run._gates`); a wait already under way runs out first.
- **The engine enforces less than the buttons do.** Blotter gates such as "no Fill on a Rejected order" are `enable.when` expressions in app.json, not engine checks, so a macro can do what a button would not offer. That is wanted (`misbehaving-counterparty`), and it is why the docs must not promise "exactly what a button can".

### In the database: `store.py`

`engine.macros` is a `MacroManager`: what `fix_cmd` talks to (`check_macro`, `save_macro`, `delete_macro`, `macro_vocab`, `list_examples`, `get_example`, `arm_macro`, `run_macro`, `stop_macro`, `pause_macro`, `resume_macro`, `move_run`, `run_loopback_tour`, `stop_run`, `pause_run`, `resume_run`, `detach_order`). The runner stays the authority on what is running; four tables are its shadow, written **in order by one worker** fed from the runner's synchronous hooks (`flush()` = runner settled and queue drained — tests call it after every inbound message).

- `fix_macros` (versioned; unique `name`; `problems` = error count at save): a Save with problems is kept as a draft, and the name a macro gives itself must equal the name it is saved under. Deleting an armed macro is refused; `delete_many(names)` (`fix_cmd delete_macro` with `names`, a list or comma-joined — the editor's Delete of a selection) checks every name first, unknown or live, and deletes whole or not at all, like Pause…/Stop… over their run lists; `delete(name)` is the one-name case.
- `fix_macro_runs`: one arming — `version` (the macro row's `_mkio_version`), `session`, `seed`, `speed`, `status` (`armed`/`paused`/`stopped`/`interrupted`), `verdict`, counters. `fix_macro_orders` (one row per subject a run took: `subject` and `order_row`, the row id in that subject's table, unique with `run_id` since ids collide across tables — the pre-0.64 `(run_id, order_row)` index is dropped at start; `cl_ord_id` is the subject's current ID whatever it is, `order_id` an order's alone; upserted on status/line/wait changes) and `fix_macro_log`. All three are archive group `data`; an online archive touching orders, trades or these tables is refused while a run is armed (`check_archive`).
- Taking a row writes its table's `macro` = `"<name> #<run id>"` (ops `tag_<table>`; every subject's table has the column, outside the engine's column lists, so no engine write touches it). `detach(order_row, subject)` names the subject, and so does the Runs window's Detach (`${row.subject}`; the tree's `subject` column).
- `setup_loopback` and the tour (`run_tour`, `TOUR_ARMED`/`TOUR_RUN`): `examples/CLAUDE.md`.
- **Restart.** `stop()` says nothing to the tables, so runs stay `armed`. `start()` (from `FixEngine.start`, after sessions load) marks every live run and live instance `interrupted` and plays **nothing** again (`_recover`). Through 0.50 a waiting-only macro was re-armed as a fresh run in its old priority; with Play/Stop on the blotters the user saw ▶ lit after a restart and called it a bug — a run is something a person started. Sending macros were never run again: **a restart never sends anything**.
- **Record first, start second.** `arm` calls `runner.arm(start=False)`, writes and registers the run's row, *then* `runner.start(run)`. A macro can fail in its first instant (`new` on a session that just dropped) and a sending-only run then ends at once; started first, the hooks found no row for the run and dropped the failure, its log line and the run's end, leaving a row that said `armed` for ever and a Stop that answered "not live" (found in use, 2026-09-20). For the same reason `runner.arm` refuses a `run` whose session is not active, `stop_run` never errors on a run that is over — it writes the row to the run's true state, or `interrupted` for a row this process never armed — and a macro that ends without ever getting an order is still a row (`order_row = -1 - index`).
- `arm(name, side=, session=, …)` checks the macro against the templates and sessions that exist and refuses errors, an unknown session and a macro of the other side (the side is the request's `side`, which the editor's dialogs send; without one `arm_macro` means `market` and `run_macro` `client`). `check_macro` answers `sends` — the macro has a `run` block — which is what the editor's ▶ picks Run… or Arm… by. See **Sides and many runs**.

### End-to-end macros (0.69)

A third kind beside the two sides: `vocab.E2E = "end-to-end"`, `MACRO_KINDS = (*MACRO_SIDES, E2E)`. It holds blocks of **both** sides and plays them in **one run**, so everything run-scoped — `signal`, `share`, the run's rows, `on signal` — crosses the sides with no rule of its own. The user chose it over cross-run signals (2026-09-27): one file is one test with one verdict.

- **Which kind a macro is.** `check(text, side=)` sets `Macro.declared`, and `Macro.side` is that, else what the blocks make it: of one side that side's, of both `end-to-end` — so a file with both checks clean without a `side` (`mkfix check`, `mkfix run`), and is a problem only in the editor of a side. In its own editor a macro is end-to-end whatever it holds so far. The store's `side` column holds the kind; `_side` takes `MACRO_KINDS`; names stay one namespace.
- **Two sessions.** `Run.session` is the client blocks', `Run.market_session` the market blocks' (`session_for(side)`, `session_of(block)`; the `market_session` column of `fix_macro_runs`, second in `insert_run`). `validate` asks for the one a `run` block of that side needs and refuses a market session on a macro of one side; `_offer` filters what arrives by the session of the block's side; an `on signal` block sends on the session of its side, else where the sender is. `Macro.needs_session`/`needs_market_session` (`needs(side)`) say which the Run… dialog must ask for; a macro of one side has the one.
- **A test comes first.** `_offer` tries the end-to-end runs before the rest, each group in arming order: an armed desk would otherwise answer the test's orders. `offered("end-to-end")` is their own line, with its own priorities (`_renumber` goes over `MACRO_KINDS`).
- **A test ends.** `_maybe_finished`: an end-to-end run that sends is `finished` when every macro of its sending blocks is over and no other is at work — `RUNNING`, or `LISTENING` with a `when` flow still going (`Instance.flows`; `_guarded` and `_changed` ask again when a flow ends or a macro runs out of lines) — and the ones left listening are stopped with it. Left armed it would go on taking what arrives, ahead of everything. One with no `run` block stays armed like any macro that waits.
- **Recording.** `EndToEndRecorder` is a client `Recorder` and a market one; `stop` joins their blocks (`_write` answers `blocks`, `counts`, `sessions` for it), the client's first, under one header. `record_start(side, session, market_session)`.
- `history.py` writes a side's macro only (`FromHistory` takes `MACRO_SIDES`), and the blotters' decks are a side's. `tests/test_macro_end_to_end.py`, `TestEndToEnd` in `test_macro_recorder.py`.

### Sides and many runs (0.49)

- **One side per macro** (but for end-to-end ones, above). `vocab.side_of(kind)`: `market` blocks make a market macro, `client` and `attached` blocks a client one (`Macro.side`). `check(text, side=)` reports every block of the other side — `side` is the pane the macro is edited in; without it the first block decides. The UI is two of everything (Client and Market menus; the `<side>-macros` editor and the `<side>-runs` window — the `<side>-macro-runs` tree over `<side>-macro-log`, see static/CLAUDE.md), all over the same four tables, each stamped with `side` and each pane filtering on it; `_backfill_sides` stamps pre-0.49 rows at startup (a run whose macro is gone counts as market). Names are one namespace: `save` refuses a name the other side holds, since runs, the log and an order's Macro column name a macro by name alone.
- **Any number of live runs**, of one macro or many. The only refusal is a run that could never be given an order: a macro with no `run` block, armed again for the same session filter. Delete is refused while any run is live; an edit is not — a `Run` holds its parsed `Macro`, and the editor marks live lines only for runs of the saved version. `stop_macro(name)` stops every live run of a macro (the editor's ■), `pause_macro(name)`/`resume_macro(name)` pause its playing runs / resume its paused ones (the editor's ⏸, which resumes once all are paused); `runner.max_live` (20,000) caps live macros across all runs, beside the per-run `max_instances`.
- **Priority.** `runner.runs` order is offer order. `Run.waits` = it has `on` blocks; `runner.offered(side)` lists those, `runner.move(run, up)` swaps neighbours of one side, and `store._renumber` mirrors each waiting run's 1-based place into `fix_macro_runs.priority` (0 = only sends, or over) after every arm, stop and `move_run`. A restart clears the line with the runs (`_recover`).

### Recording and history: `recorder.py`, `history.py`

How the recorder turns what was done by hand into a macro, and how a macro is written from a row's recorded messages, is in `RECORDING.md` beside this file — read it before touching either module.

### The order blotters' controls (0.51)

`play(side, what, …)` — one choice or several joined by commas (the dialog's checklist): `macro:NAME`/`needs:NAME` arms/runs it, `resume:ID|all` resumes that side's paused runs; every choice is checked first (`_armable` + `runner.validate`, the refusals of `arm` without its effects), so a list is played whole or not at all, and one session, speed and seed serve all; `pause_runs(side, run="")` and `stop_runs(side, run="")` take one run by row id or the whole side (`_side_runs` refuses a run of the other side or in the wrong state); `record_stop(side, name, save=True)` checks the name is free *before* stopping (a clash leaves it recording), saves only when something was recorded, and answers `saved`; `status()` is both sides' recordings for the UI's poll (`fix_cmd` `play_macro`, `pause_runs`, `stop_runs`, `macro_status`). `fix_macros.needs_session` is written at save so the Play… dialog can require a session only where the macro names none.

### Time and quiescence: `clock.py`

A flow is parked only in `_sleep`, `_wait` and `_gate`. `Scheduler` keeps the *set* of busy flows: `wake(flow, future, value)` marks the flow busy before resolving its future, parking and ending clear it, and both are idempotent — which is what makes cancelling a flow at any point safe. `settle()` returns when no flow is busy; busy includes awaiting a real database commit inside `perform`. `VirtualClock.advance(seconds)` fires due timers one at a time, settling after each, so tests run minutes of macro in the time their writes take and are deterministic (`seed` drives `RANDOM()` and jitter through a per-instance `random.Random(f"{seed}:{index}")`). Tests follow every inbound message with `await runner.settle()`.

## Rules the examples fixed

- A macro with live top-level `when` lines stays alive after its last plain line has run, until `stop`, a verdict, or the end of the run: `cancel-replace-desk` refuses a too-late cancel after the order has filled, `dispute-desk` answers disputes after its only fill.
- For one event the first matching `when` wins; handlers run beside the main flow; an instance's actions go one at a time.
- A re-notified fill is a new trade (the engine infers nothing); `event.prev` is how a macro tells it from a fill that moved CumQty.

## From the command line: `cli.py` (0.65)

`mkfix check FILE…` and `mkfix run FILE` (`__main__.main` dispatches them ahead of argparse, like archive/restore). `check_files` is offline — `check(text, side=)` per file, every diagnostic as `FILE:LINE:COL: severity: message` (columns from 1), exit 1 on any error, 3 on a file it cannot read; templates and sessions are unknown there and pass. `run_file` talks to a running server through `MkioClient.send("fix_cmd", …, op=…)` — `fix_cmd` takes the UI's transaction-shaped messages, **not** `request` (a reqrep) — refuses a macro with errors before sending anything, saves it under the file's stem (`--name` overrides; Import's rule), then `run_macro` or `arm_macro` by its side. `--wait`/`--for D` poll `fix_cmd run_report` (`MacroManager.report(run_id, after)`: the run row, its `fix_macro_orders` rows, log lines with id > `after`, `sends` and `sending` — any live generator or `run`-block instance, from the runner) every 250 ms, printing new log lines, until the run is over; a run that sends and also waits is stopped once nothing of it is sending, and any run when `--for` runs out. Exit 0 passed or no verdict, 1 failed, 2 interrupted, 3 usage or no server. Real answers take real time: the end-to-end test (`test_cli.py::test_run_follows_a_run_to_its_verdict`, a server subprocess with loopback sessions on free ports) runs at speed 4, since at 20 the examples' 2 s bounds are 100 ms and flake.
