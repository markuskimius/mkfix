# mkfix/static — the scenario UI

The rest of the UI is described in the root CLAUDE.md. This file covers what scenarios added.

## Rule: the browser knows no word of the language

Everything the editor knows comes from the server: the vocabulary (`fix_cmd scenario_vocab` → `mkfix/scenario/vocab.vocabulary()`) drives colouring, completion and F1 help, and `check_scenario` supplies the problems it underlines. The Python parser alone decides what a script means; colouring that is slightly off can never make a bad script look accepted. Do not list verbs, events or terms in JS — `test_scenario_ui.py::test_every_word_of_the_vocabulary_is_coloured` holds the rules to the vocabulary.

## Files

- `scenario-lang.js` — pure functions, tested under node: `buildRules(vocab)` (one ordered regex list, first match at a position wins), `aceRules(vocab)` (the same without the one lookbehind rule, for Ace), `tokenizeLine`/`highlight` (the Help viewer colours code blocks with the same list), `blockKindAt`, `completionsAt(vocab, lines, row, col, extras)` (headers at the top of the file; verbs and statements valid for the block's side at the start of a line; events after `when`/`wait`/`expect`; a verb's unused terms, trade targets and `using`; enum words after `side:` etc.; template names after `using '`; `on` after `run` and session names after `run on`; `extras.side` narrows the block headers offered to the editor's side; fields after `order.`/`trade.`/`event.`/`event.prev.`; otherwise context names and functions), `helpAt`.
- `panes/scenarios.js` — list + Ace editor, registered once and used twice: `client-scenarios` and `market-scenarios` differ by `spec.side`, which the pane passes to `check_scenario`/`save_scenario`/`list_examples`, puts in every subscription's `filter` (`side == '…'`), and uses to pick the dialog (`run_scenario` with `row.needs_session`/`row.session` from the last check, or `arm_scenario`). A live run never disables Run…/Arm… (the server refuses the one pointless repeat); the badge counts runs and live scripts, Stop is `stop_scenario` (every live run of the open script), Delete waits for them, and live-line marks cover every live run of the saved version. `open_example` is `{name, side}` and each editor takes only its own. Ace is vendored prebuilt in `vendor/ace` (ace-builds 1.44.0: `ace.js`, `ext-language_tools.js`, `ext-searchbox.js`, `keybinding-vim.js`, `LICENSE`) and loaded as classic scripts on first use; `basePath` lets Ace fetch the vim keybinding itself. Our mode, indentation folding and theme are `ace.define`d at run time; the theme module carries no CSS — `.ace-mkfix` rules live in `mkfix.css` on mkui's variables. `useWorker: false` (there is no worker file). Check runs 300 ms after typing stops, guarded by a sequence number so a late answer to old text is dropped; diagnostics become annotations plus `scn-mark-*` markers. Save is allowed with problems (a draft); Run…/Arm… needs a saved, clean script. Live scripts' lines are marked from `scenario_instances_query` when the text is unedited. vim: `localStorage` `mkfix.scenario.vim`, `:w` = Save. F1 sets `app.state.help_target`; the Runs selection (`selected_scenario_instance`) moves the cursor; `open_example` (set by the Help viewer) opens a copy of a bundled example. Arm… is `app.dialog("arm_scenario", { row: { name } })` — a named dialog in app.json, not modal, like every mkfix dialog.
- `markdown.js` — the renderer for help pages: headings with slug ids, paragraphs, nested lists, fenced code (optional `highlight(code, lang)`), tables with `\|`, rules, inline code/bold/italic/links; HTML is escaped and only `http(s)`, `#…` and relative links survive. `headings(text)` feeds the contents list.
- `panes/help-viewer.js` + `help/index.json` + `help/*.md` — the Help pane. A page is a Markdown file, or `builtin: "examples"`, which is built from `fix_cmd list_examples` (the examples' header comments) with **Open in editor**, and carries **Set up loopback sessions** (`fix_cmd setup_loopback`). Links to `other.md#anchor` navigate inside the pane. The pages are the user documentation and are linked from the README; they must keep to what `markdown.js` renders, their `scenario` code blocks must check clean, and the reference's Actions/Events/context tables must equal the vocabulary — `test_scenario_ui.py::TestHelpPages` enforces all three.
- app.json: per side (`client`, `market`) an editor pane `<side>-scenarios` (`type: scenarios`, `side`) and three declarative tables filtered `side == '<side>'` — `<side>-runs` (Pause/Resume/Stop, Move Up/Move Down → `move_run`, single-select, gated on `priority > 0`), `<side>-scripts` (Detach; publishes `selected_scenario_instance`), `<side>-log` — identical but for the side (`test_the_two_sides_panes_differ_only_by_side`); `help-viewer`; dialogs `arm_scenario`, `run_scenario` (session `required: "row.needs_session"`) and `scenario_keys`; menus **Client** (Sent Orders, Received Trades, ―, its four scenario panes), **Market** (Received Orders, Sent Trades, ―, its four) and **To Do** (IOIs, Allocations, Replay Control — panes not yet given a side; there is no Trading menu) (`TestMenubar.PANES` pins every pane menu's contents); Help menu leads with Scenario Language and Scenario Editor Keys; a `scenario` column on both order blotters. `test_every_declared_dialog_is_opened_by_something` accepts a dialog opened by a menu or by a pane's literal `app.dialog("name"`. The Examples page groups by side, opens an example in its side's editor, and carries **Set up loopback sessions** and **Run the loopback tour** (`run_loopback_tour`).
