# mkfix/static — the macro UI

The rest of the UI is described in the root CLAUDE.md. This file covers what macros added.

## Rule: the browser knows no word of the language

Everything the editor knows comes from the server: the vocabulary (`fix_cmd macro_vocab` → `mkfix/macro/vocab.vocabulary()`) drives colouring, completion and F1 help, and `check_macro` supplies the problems it underlines. The Python parser alone decides what a macro means; colouring that is slightly off can never make a bad macro look accepted. Do not list verbs, events or terms in JS — `test_macro_ui.py::test_every_word_of_the_vocabulary_is_coloured` holds the rules to the vocabulary.

## Files

- `macro-lang.js` — pure functions, tested under node: `buildRules(vocab)` (one ordered regex list, first match at a position wins), `aceRules(vocab)` (the same without the one lookbehind rule, for Ace), `tokenizeLine`/`highlight` (the Help viewer colours code blocks with the same list), `blockKindAt`, `completionsAt(vocab, lines, row, col, extras)` (headers at the top of the file; verbs and statements valid for the block's side at the start of a line; events after `when`/`wait`/`expect`; a verb's unused terms, trade targets and `using`; enum words after `side:` etc.; template names after `using '`; `on` after `run` and session names after `run on`; `extras.side` narrows the block headers offered to the editor's side; fields after `order.`/`trade.`/`event.`/`event.prev.`; otherwise context names and functions), `helpAt` (one line for F1, with the word's `start`/`end`), `hoverAt` (the hover: `helpAt` plus an action's terms and trade targets, and `word = code` for an enum word given to a term; nothing inside a string or a comment). The pane shows it through Ace's `HoverTooltip` (`ace/tooltip`), leading with the row's problem when there is one; Ace hangs that tooltip on `<body>` with the theme class on the tooltip itself, hence `.ace_tooltip.ace-mkfix` in mkfix.css.
- `panes/macros.js` — list + Ace editor, registered once and used twice: `client-macros` and `market-macros` differ by `spec.side`, which the pane passes to `check_macro`/`save_macro`/`list_examples`, puts in every subscription's `filter` (`side == '…'`), and uses to pick the dialog (`run_macro` with `row.needs_session`/`row.session` from the last check, or `arm_macro`). The toolbar is `[New] [Clone] [Save] [Delete] [History] | [●] [▶] [⏸] [■]` left and `[Example…] [Import] [Export] vim ?` right (`test_the_editor_toolbar_is_ordered_like_the_blotters` pins it): the deck is the blotters' four symbols in the blotters' order, the same `macro-control` classes and lit states, but about the open macro — ▶ opens Run…/Arm… (a live run never disables it: the server refuses the one pointless repeat), ⏸ is `pause_macro` (every playing run of the macro) or, once all are paused, `resume_macro`, ■ is `stop_macro`, ● records (below). **Clone** is a Save As: the text shown — the macro, its unsaved edits, or the version being viewed — saved under `<name> copy` (then `copy 2`…), the original left as saved, so it asks only the name. **Delete** takes the list's selection: a plain click opens a macro and is the selection (`open()` sets it, whichever way a macro was opened), Ctrl/Cmd-click toggles one, Shift-click ranges from the last plain click (`pick`; `macro-selected` rows), the button reads `Delete (N)`, waits for every selected macro's runs, and sends `delete_macro` one `names` list, taken whole or not at all; the badge counts runs and live scripts, and live-line marks cover every live run of the saved version. `open_example` is `{name, side}` and each editor takes only its own. **●** asks for a session (`.macro-ask` bar), calls `record_start`, then pulses red with the action count in its tooltip from a 1.5 s `record_status` poll (the recording is the server's: a reopened pane finds it again); stopping asks for a name first (`askName(suggested, option)`: with an `option` it shows a tick box and answers `{ name, ticked }` — here "Keep my delays", sent as `delays`; the blotters' `stop_recording` dialog has the same checkbox) — cancelling leaves it recording — then `record_stop`, saves the text under that name and opens it. `open()` returns its check's promise so a caller's status line is not overwritten by "No problems". Ace is vendored prebuilt in `vendor/ace` (ace-builds 1.44.0: `ace.js`, `ext-language_tools.js`, `ext-searchbox.js`, `keybinding-vim.js`, `LICENSE`) and loaded as classic scripts on first use; `basePath` lets Ace fetch the vim keybinding itself. Our mode, indentation folding and theme are `ace.define`d at run time; the theme module carries no CSS — `.ace-mkfix` rules live in `mkfix.css` on mkui's variables. `useWorker: false` (there is no worker file). Check runs 300 ms after typing stops, guarded by a sequence number so a late answer to old text is dropped; diagnostics become annotations plus `macro-mark-*` markers. Save is allowed with problems (a draft); Run…/Arm… needs a saved, clean script. Live scripts' lines are marked from `macro_orders_query` when the text is unedited. vim: `localStorage` `mkfix.macro.vim`, `:w` = Save. The list's edge (`.macro-splitter`, which carries the border) drags its width and double-clicks to fit the longest name, badge included; `mkfix.macro.list` remembers it for both editors. F1 sets `app.state.help_target`; the Runs selection (`selected_macro_order`) moves the cursor; `open_example` (set by the Help viewer) opens a copy of a bundled example. Arm… is `app.dialog("arm_macro", { row: { name } })` — a named dialog in app.json, not modal, like every mkfix dialog.
- `line-diff.js` — pure, node-tested: `lineDiff(from, to)` (LCS over lines after trimming the common head and tail; above 4M table cells the middle is all `del` then `add`), `diffMarks(from, to)` → `only` (rows of `from` that `to` lacks) and `gaps` (`{row, count}`: lines of `to` that belong before `from`'s `row`), `splitLines`. **History** in `panes/macros.js` uses it: `macro_versions` (a reqrep over `fix_macros__history` by row `id`, newest first — so a macro deleted and rewritten starts afresh) fills a panel right of the editor, each version with the runs whose `version` it is; clicking one sets `viewing`, stashes the editor's text in `draft` (so `dirty()` still speaks for the macro, via `text()`), shows the version read-only and marks it against `saved` (`macro-diff-only` lines, `macro-diff-gap` ▸ gutter). While `viewing`, Save, ▶ and the check are off. Restore = `backToScript(source)`: the version becomes an unsaved edit and the next Save is a new version — no mkio undo, nothing lost. `test_history_is_wired_to_the_versions_the_server_keeps` checks the columns the pane reads against the service's SQL.
- `macro-status.js` + `macro-status-lib.js` — always loaded (index.html), and no pane: it is the `macro-status` status bar widget (app.json `statusbar.right`), and a widget factory is handed the `app`, which is how it boots. It keeps `state.macros.client`/`.market` = `sideState` (`recording`, `actions`, `session`, `playing`, `paused`, `live`, `orders`, `runs`, `last`) from a `macro_runs_query` subscription plus a `macro_status` poll (3 s, 1 s while recording — a recording lives in the server and may have been started elsewhere); renders `statusItems(state)` as links (`pane.show`); and mounts a control group — ● ▶ ⏸ ■ (record, play, pause, stop: the editors' toolbar order), symbols only at the user's request, the words in `title`/`aria-label`; lit by state like a tape deck — ▶ `macro-playing` while `playing > 0`, ⏸ `macro-paused` while `paused > 0` (even when disabled), ● red and pulsing while recording, counts in the tooltips — into `order-blotter` (client) and `market-order-blotter` (market) through mkio-table's `_toolbar.extras()` slot, mounting when the pane's `_ready` resolves (a MutationObserver notices a pane arriving — waiting for the next poll left the toolbar bare for seconds) and re-mounting when a pane is rebuilt; the rule before the group has the same space either side only because its `margin-left` makes mkui's 6px toolbar `gap` up to its `padding-left` (tested against mkui's stylesheet). While `mkio.connected` is false it drops its picture (runs and recordings) and the controls are dark and disabled — a restart stops every macro (`_recover` re-arms nothing), and the reconnect's snapshot says what is true. **Why not declared buttons:** mkui re-evaluates a button's `enable.when` on selection, data and connection changes, never on app state, and a label is fixed; these must follow state. The buttons open named dialogs (`play_macro`, `pause_runs`, `stop_runs`, `record_macro`, `stop_recording`; context `row.side`/`row.Side`) whose checklists are fed by the `macro_play_options`/`macro_run_options` reqreps — a Play… value is `resume:ID`, `macro:NAME` or `needs:NAME` (a macro naming no session), so `CONTAINS(what, 'needs:')` makes the session required and `CONTAINS(what, 'macro:') or …'needs:'` shows session, speed and seed; safe because a macro name can hold neither `:` nor `,` (tested) — and which fire `macro.refresh` / `macro.recorded` (`submit.then`; registered here — an action's first argument is the app). `macro.recorded` shows the side's editor and sets `open_macro`, which the editor waits on (the row may still be arriving; none means nothing was recorded). Templates are mkio expressions: `IF(…)`, never `?:` (tested). Pause… and Stop… show their runs as a `checklist` (mkui 1.11.0: tick boxes in a scrolling box, `all` row, `value: "*"` = open with everything ticked, `required` = tick at least one); it submits `runs` as ids joined by commas, which `_side_runs` takes whole or not at all. A fetched select's blank row is named by `optionsFrom.empty` (mkui 1.11.0) — mkui never merges a static `options` list into a fetched one, so six dialogs' "(any session)"-style labels had silently shown a dash; `test_a_fetched_select_names_its_blank_choice_the_way_mkui_reads_it` forbids the dead form. The lib is pure and node-tested: ended runs are news for 60 s, a failed one until a later run on its side, 10 min at most; FIX stamps are UTC.
- `markdown.js` — the renderer for help pages: headings with slug ids, paragraphs, nested lists, fenced code (optional `highlight(code, lang)`), tables with `\|`, rules, inline code/bold/italic/links; HTML is escaped and only `http(s)`, `#…` and relative links survive. `headings(text)` feeds the contents list.
- `panes/help-viewer.js` + `help/index.json` + `help/*.md` — the Help pane. A page is a Markdown file, or `builtin: "examples"`, which is built from `fix_cmd list_examples` (the examples' header comments) with **Open in editor**, and carries **Set up loopback sessions** (`fix_cmd setup_loopback`). Links to `other.md#anchor` navigate inside the pane. The pages are the user documentation and are linked from the README; they must keep to what `markdown.js` renders, their `macro` code blocks must check clean, and the reference's Actions/Events/context tables must equal the vocabulary — `test_macro_ui.py::TestHelpPages` enforces all three.
- app.json: per side (`client`, `market`) an editor pane `<side>-macros` (`type: macros`, `side`) and three declarative tables filtered `side == '<side>'` — `<side>-runs` (Pause/Resume/Stop, Move Up/Move Down → `move_run`, single-select, gated on `priority > 0`), `<side>-macros` (Detach; publishes `selected_macro_order`), `<side>-log` — identical but for the side (`test_the_two_sides_panes_differ_only_by_side`); `help-viewer`; dialogs `arm_macro`, `run_macro` (session `required: "row.needs_session"`) and `macro_keys`; menus **Client** (Sent Orders, Received Trades, ―, its four macro panes), **Market** (Received Orders, Sent Trades, ―, its four) and **To Do** (IOIs, Allocations, Replay Control — a declarative table since 0.54, notes in `fix/CLAUDE.md`; panes not yet given a side; there is no Trading menu) (`TestMenubar.PANES` pins every pane menu's contents); Help menu leads with Macro Language, Macro Editor Keys and Replaying a Log (`help-replay`, a second `help-viewer` pane whose `page` opens that Markdown page; `TestHelpMenu.test_menu_shape` pins the menu); a `macro` column on both order blotters. `test_every_declared_dialog_is_opened_by_something` accepts a dialog opened by a menu or by a pane's literal `app.dialog("name"`. The Examples page groups by side, opens an example in its side's editor, and carries **Set up loopback sessions** and **Run the loopback tour** (`run_loopback_tour`).
