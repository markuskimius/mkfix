# mkfix/fix — actions, events and the order lock

What scripted macros stand on, and what the order and trade buttons do.

## One way in: `FixEngine.perform(op, data, source)`

`actions.py` holds `ACTIONS`: every order, trade, IOI, advert and allocation action by its `fix_cmd` name, each a small coroutine turning a loosely typed payload (a dialog submits strings) into the engine call and naming what it returns (`cl_ord_id`, `order_id`, `exec_id`). `FixCommandService._dispatch` hands any command in `ACTIONS` to `perform` — `save_as` templates are saved first, a UI concern — and keeps only the session, replay and dictionary commands as branches of its own; `test_ui_config._fix_cmd_commands` is the union the app.json guards check against. A script calls the same `perform` with `source="macro"`, so it can do exactly what a button can, behind the same refusals (`_active_session`, `_require_live_trade`, the Restate checks). `ORDER_KEY`/`TRADE_KEY` name the payload key carrying the action's subject; `test_events.TestPerform` holds the table to `TEMPLATE_TERMS`.

## Events: `events.py`

`engine.events` is an `EventBus`: synchronous fan-out to listeners that must not block (they run on a session's read loop or inside an action); one that raises is logged and skipped. **Nothing listens until something subscribes**, and with no listener the engine skips the row reads an event costs (`events.active`).

An `EngineEvent` has `kinds` (most specific first; `kind` is the first), `session_id`, `source` (`wire` / `manual` / `macro`), `order` and `prev` (the order row after and before — what lets a listener tell a fill that moved CumQty from a re-notified one, which the engine deliberately records as a new trade and infers nothing about), `trade`, `msg`, `request` (the ClOrdID a request or its answer names) and `detail`. `order_key` is `fix_orders.id`, the identity that survives every rename.

Every event is emitted **after its writes have committed** (`writer.submit` returns on commit), so a listener that queries finds what the event describes.

| Emitted by | kinds |
|---|---|
| `_handle_new_order` | `order`, `message` |
| `_handle_cancel_request` | `cancel` or `replace`, `message`; a request naming no order is `message` alone (`detail.unknown_order`) and is still auto-rejected |
| `_handle_execution_report` | `report_kinds(msg)` — `ack` `rejected` `canceled` `replaced` `pending` `expired` `done for day` `restated` `fill` (+ `filled` when 39=2) `corrected` `busted`, then `er`; from 150, from 39 where a dialect has no 150, and from 20 for a 4.2 bust/correct. A report that *creates* its order row (Message Replay sends around `send_new_order`) announces `sent order` first |
| `_handle_cancel_reject` | `cancel rejected`, `message`; `detail.response_to` (`cancel`/`replace`), `detail.reason` (102's name) |
| `_handle_dont_know_trade` | `dk`, `message` — only when it names a trade we sent |
| `update_session_state` | `session up` / `session down`, when a session's ACTIVE-ness flips; no order (`detail.status`) |
| `send_new_order` | `sent order` — after the row is written and **before the send**, so whoever takes the order owns it before an acknowledgement can arrive; `source` and `detail.tag` say who sent it |
| `perform` | `action` (`detail.op`, `detail.result`, `detail.data` — the payload as given, minus `_` keys — and `detail.trade_before`, the trade row as the action found it: what the macro recorder writes scripts from), `send_new_order` included. The subject is found before the action (an accepted replace renames it) and re-read after by row id. A refused action announces nothing |

## The order lock

`_market_action` decorates the eleven market-side actions (accept/reject order, fill, unsolicited cancel, restate, accept cancel/replace, reject cancel, correct, bust, re-notify). The decorated body loads its order, builds the answer and submits its writes, returning `(message, result)`; the wrapper holds `_order_lock(session_id)` across that, **then sends with the lock released**. `_handle_cancel_request` takes the same lock around its load and write.

Why: these actions write the whole of `ORDER_UPDATE_COLS` back from the snapshot they loaded, so a cancel/replace request parked between the load and the write lost its `pending_*`. A hand on a button rarely hit it; a script answering at wire speed would. The send stays outside because it awaits and the counterparty's answer may be handled inside it — by a handler that needs the lock (`test_the_lock_is_not_held_across_the_send`). One lock per session, not per order: an accepted replace renames the key an order would be locked by, and the sections are short. The client side needs none — its writes are single statements since 0.45 (the request slot ops).

## Order and trade actions

Received Orders drives everything through one Accept/Reject pair (`accept_request`/`reject_request`) plus Fill (`fill_order`): a new order arrives as `pending_action` "New", and inbound OrderCancelRequest (35=F) / OrderCancelReplaceRequest (35=G) park as "Cancel"/"Replace" with the request's ClOrdID and terms in the `pending_*` columns — `status` is untouched, so fills stay possible while a request is pending, and both buttons gate on `pending_action` alone. Fill, Unsol Cxl (`unsolicited_cancel`, template scope `unsolicited`: ER Canceled without 41, so no rename) and Restate (`restate_order`, scope `restate`, term `restate_reason`: ER 150=D without 41 — working 39, new 38, 44 unless blank, 378 from a hand-listed dropdown; rewrites `order_qty`/`price`; refuses a qty below CumQty or a dictionary without 150=D, i.e. 4.0/4.1) gate on the non-dead statuses (`Filled` included — overfilling is a scenario; only `Canceled`/`Rejected` block them), always under the row's current ClOrdID; each consumes a not-yet-accepted order's pending New, which the ER implicitly acknowledges; a pending Cancel/Replace stays parked, so a too-late reject can follow the cancel. Sent Orders' Replace allows `Filled` too, so a filled order can be replaced up. The dispatchers route to `accept_order`/`accept_cancel`/`accept_replace` and `reject_order`/`reject_cancel` (also `fix_cmd` ops); accepting a cancel/replace sends an ER answering the request's ClOrdID (tag 11, superseded ID in 41) and moves the order row to it via the `rename_order` op — on both sides a row's ClOrdID is the chain's latest accepted ID, and the immutable `order_id` is the stable identity. Rejecting a request sends OrderCancelReject (35=9) with CxlRejResponseTo(434) and leaves the ClOrdID alone; requests naming an unknown order are auto-rejected. The order upsert guards `order_qty`/`price` with iif against an ER lacking 38/44. Sent Trades drives `correct_trade`/`bust_trade` (codes per `wire_exec_codes`), always with ExecRefID(19) — a trade is one row (`id`) and a correction or bust rewrites it as a new version (`update_execution`, keyed by the row id): the live row carries the latest ExecID, `exec_ref_id` (the ExecID answered, as tag 19 went out), `exec_type` ("Correct"/"Cancel", or "TradeCorrect"/"TradeCancel" on 4.3+) and terms; the fill and earlier corrections stay in `fix_executions__history`. `_find_execution` resolves an ExecID against the live row, then history, so a bust naming the original fill after a correction lands on the corrected trade (`_load_execution` too). A busted trade is done — `_require_live_trade` refuses further corrections or busts by `exec_type` name (`BUSTED_EXEC_TYPES`; code 1 means Cancel on one dialect and PartialFill on the other) and the Correct/Bust/DK gates exclude the same names, busted rows muted (`rowStyle`). Received Trades drives `dk_trade` (DK button): a DontKnowTrade (35=Q) answering the counterparty's ER with its OrderID(37)/ExecID(17), DKReason(127) from a hand-listed dropdown (tested against the dictionaries) and optional Text(58); it marks the received row's `dk_reason`/`dk_text` as sent (before the send, undone if it fails; nothing on a TX row, where they arm Re-notify), and OrderQty(38) is the order's current, by the trade's `order_id` (`_order_qty_of`; CumQty+LeavesQty once the order is gone). An inbound 35=Q marks the sent trade its ExecID(17) names (`_handle_dont_know_trade`, via `_find_execution`, so a DK of the fill after a correction lands on the corrected trade): `dk_execution` writes DKReason(127)'s enum name and Text(58) into `dk_reason`/`dk_text` (a new row version, terms untouched, Correct/Bust still allowed, Sent Trades' "DK" column), a correction or bust blanks them (`EXEC_UPDATE_COLS`) since the DK answered an ExecID the row no longer carries, and a Q naming an unknown or received ExecID stays a recorded message. Re-notify (`renotify_trade`; gated on `dk_reason` alone, so a DK'd bust qualifies; the engine refuses an un-DK'd trade) restates the row's report — fill, correction or bust by `exec_type` name — under a fresh ExecID, with the row's terms and `exec_ref_id` and the order's current state: a new row version, DK blanked, no order write. Extras can recast it (`20=0|19=`), so kind and reference come from `_as_sent`. New orders go through the Sent Orders "New" dialog (hand-listed Order Type/TIF options, tested against the dictionaries). Clone (both order blotters; one row, any status) is the New form prefilled from the row like Replace, session editable, Text from `sent_text` (`text` on Received Orders), minus the Template dropdown, whose remembered pick would re-run its `fill` over the prefills (`TestClone`). Nothing narrows 40/59 by the session's version; a `showWhen` note only advises. Every order/trade dialog labels fields with their tag, lists options as `code - name`, and closes with a computed "Terms as tags" line; New and Replace fold Expire and `save_as` into an `Advanced` section above it (mkui `group`; no `remember`); the session dropdown is fed by `sessions_list`, a reqrep, since `optionsFrom` uses request-reply. No Account field: it rides as an extra tag (`1=...`). Replace opens the same form (session read-only; `session_id`/`orig_cl_ord_id` ride as `rowData`) prefilled from the row's last accepted terms (New's or the last accepted Replace's): `symbol`/`side_code`/`ord_type_code`/`tif_code`/`extra_tags`/`expire_time`/`expire_date` plus `entered_qty`/`entered_price` (`ENTERED_COLS` in engine.py). Expire is one mkui `datetime` field (`time: "optional"`) submitting a bare date or a UTC ISO-8601 instant as `expire_time`; `FixMessageFactory.expiry` maps a bare date (`is_bare_date`) to ExpireDate(432) and an instant to ExpireTime(126) via `normalize_expire_time` (a FIX stamp at the session's `timestamp_precision`, or the `fix_cmd` ops' `expire_precision` override; FIX-form input passes as written unless a precision was asked for, other text verbatim), `normalize_expire_date` turns `YYYY-MM-DD` into `YYYYMMDD`, and `_add_expiry` emits 126/432 only when non-empty and defined by the dictionary (432 joined in 4.2). The columns hold the stamps as sent (received orders record the inbound tags); Replace prefills from whichever is set through `parse` formats covering both. `send_new_order` writes them at insert; `send_cancel_replace` parks them in the slot (`pending_entered`, JSON) and the accepting ER promotes them (`_promote_entered`; a no-op for an unknown order — the request still goes out); they sit outside `ORDER_UPDATE_COLS`, so the counterparty's ERs never touch them, while `order_qty`/`price` remain the working terms an accepting ER sets. `entered_price` is NULL for market orders; tag 59 goes on a cancel/replace only when `tif` is given; `_backfill_entered_terms` seeds older rows at startup.

## Identity rules

Identity rules the engine enforces:
- `fix_orders.order_id` is write-once: the upsert SQL guards it with an `iif` (like `order_qty`/`price`) so an inbound ER's OrderID(37) can't replace the locally minted OR id on a sent order. Minted at `send_new_order` / `_handle_new_order` (arrival, not accept). Their OrderID(37) lands in `market_order_id` ("Market Order ID" on Sent Orders): the upsert and `resolve_request` take it from every ER/OrderCancelReject carrying one, a message without 37 keeps it; blank on received orders. `fix_executions` carries the same pair: a received trade's `order_id` is its order's own and `market_order_id` the ER's 37 (what `dk_trade` sends as 37; blank on sent trades), shown on Received Trades; Macros load trades by `order_id` on both sides.
- A ClOrdID chain advances only on accept: `_handle_execution_report` resolves its row (`_find_order_for_report`: tag 11 live, the request slot, then 41 live or through history) and renames when 150 (39 where absent) is 4/5; any other ER, PendingCancel/PendingReplace included, upserts under the row's current ClOrdID. `rename_order` no-ops if a row already holds the target (duplicate ER), keeping the unique index safe.
- A sent order's `pending_*` (`PENDING_COLS`) is its request slot: `send_cancel`/`send_cancel_replace` fill it before the send (`_record_entered(request=)`, op `record_request`; `_send_request` clears it on a failed send), an inbound ER keeps it (`keep_pending`), and only the answer to the ClOrdID it holds clears it — the accept's `rename_order`, or `_handle_cancel_reject` (35=9, op `resolve_request`), which also writes 39 as `status` (not under 102=1), 58 as `text`, and `cxl_rej_reason` ("Rej Reason": kind from 434, else the slot, else `_sent_request_kind`; plus 102's name). One slot, the latest request; a Replace accepted after losing the slot takes `entered_qty`/`entered_price` from the ER's 38/44 (`TestSentRequests`).
- `fix_executions.trade_id` is the immutable trade identity: minted at fill and kept through corrections/busts, new versions of the fill's row (the row `_load_execution` finds, or ExecRefID(19) resolves to live or through history; an unresolvable reference starts a new trade).
- `correct_trade`/`bust_trade` resolve the order via the execution row's `order_id`, not its fill-time `cl_ord_id` — an accepted replace renames the chain, so the stored ClOrdID may match no order row. The outgoing ER carries the order's current ClOrdID (tag 11).

## Instruments: `instrument.py`

Options, futures and futures options are an order's instrument, not a family. `fix_orders` and `fix_executions` carry `ORDER_INSTRUMENT_COLS`: the instrument (`INSTRUMENT_COLS`: `security_type` 167, `maturity`, `strike_price` 202, `put_or_call` 201, `cfi_code` 461, the underlying's 310/311/313, `multiplier` 231, `security_exchange` 207, `security_id`/`security_id_source` 48/22), the position terms (`open_close` 77, `covered_uncovered` 203) and `instrument`, the display text (`instrument_text`: `ES Dec26`, `AAPL 18Dec26 250 C`). Rows hold one spelling (167's code, `YYYYMM`/`YYYYMMDD`, words for Put/Call and the position terms, strike and multiplier REAL or NULL); `normalize_instrument` makes it from typed terms.

- **Out** — `instrument_pairs(dictionary, row, originating)`, through `FixMessageFactory.stamp_instrument`: only tags the dictionary defines (4.0 has no 167); a date splits into 200+205 where 205 exists (4.1/4.2); on 4.3, which replaced 167's FUT/OPT and 201 with CFICode, a future or option goes out as 461 (the one given, else `derived_cfi`) and no 167. A 167 value the dictionary lacks (OOF/OOP/OOC before 5.0) is refused on an order we originate — before a ClOrdID is minted — and echoed as it stands on an answer (`originating=False`). Extras override as ever.
- **In** — `instrument_of(msg)` (200+205 joined, 541 when 200 is absent, a CFI-only 4.3 message's type and Put/Call from the code). The tags are in `CONSUMED_ORDER_TAGS`/`CONSUMED_EXEC_TAGS`, so they are not echoed as extras.
- **Write-once** — the columns are in `ORDER_COLS`/`EXEC_COLS` but not the update lists: an order's instrument is what it went out with (`_sent_order_row`, from `_as_sent`) or arrived with, a report never rewrites it (one creating its row sets it), a trade's is its report's when the report names one (`carries_instrument`), else its order's. `_order_params`/`_exec_params` fill them blank, and `instrument` from the row, for writers that build none.
- **Answers** — `_stamp_order` puts the order's (a DK's: the trade's) client and instrument on every market answer but OrderCancelReject; cancel and replace requests carry the order's (`_stamp_order_instrument`).
- **Saved** — `fix_instruments` (Config › Instruments; versioned, `config` group) keeps named sets of `INSTRUMENT_COLS` plus `symbol`, saved as given whatever the version, through `fix_cmd` `save_instrument`/`delete_instrument`. Rows never name one: a dialog's pick fills its fields.

- **UI** — New and both Clones carry one `Instrument` section after Symbol/Side (generated alike; `TestInstrumentFields`): a `_instrument` pick over `instruments_list` whose `fill` copies a saved instrument into the fields, the fields (rows gated on the security type by `showWhen`), Open/Close and Covered, and `save_instrument_as`, which `fix_cmd` saves before the send. The dropdowns offer codes (`1 - Call`), so prefills from a row map its words back, and `instruments_list` returns Put/Call as the code. Replace shows the order's `instrument` read-only and sends its instrument as `rowData`, so a Save-as from Replace keeps it. The instrument terms are order template terms (`ORDER_TERMS`, `fix_templates` columns, the Templates editor for scope `order`). The blotters show `instrument` in Symbol's place. Config › Instruments (pane `instruments`, `instruments_query`) has New/Edit/Clone/Delete over `save_instrument`/`delete_instrument`.

- **Families (0.76)** — `fix_iois`, `fix_adverts`, `fix_allocations` and `fix_rfqs` carry `FAMILY_INSTRUMENT_COLS` (the instrument, no Open/Close or Covered), read by `family_instrument` in the column mappers (an RFQ's from its first 146 instance) and consumed. `send_ioi`/`send_advert`/`send_allocation`/`send_rfq`/`send_quote` take `instrument` (refused before the ID is minted); the builders stamp only `INSTRUMENT_COLS`; a Replace, a Cancel and every answer (quote, requote, AJ, AG) carry the row's. A QuoteRequest's and a QuoteRequestReject's ride in the 146 instance after 55 (`_stamp_group_instrument`; the body through 4.1). An order naming none takes the IOI's (23) or the quote's (117; `_answered_instrument`), a Hit's order the quote's (`_order_from_response`), an allocation naming none its first order's. Unsolicited quote streams are matched by instrument too (`_live_quote_chain`), so two series of one symbol are two rows. RFQ requests stay symbols only. `_backfill_family_instrument` (fix_settings `family_instrument_backfill`). `tests/test_family_instruments.py`.

`_backfill_instrument` (fix_settings `instrument_backfill`) shows older rows by symbol. `tests/test_instruments.py`; the per-version tag matrix is pinned in `tests/test_dictionary.py`.

## Lists: `lists.py` (0.77)

A list is every order of one ListID(66) on a session and side. `fix_lists` (`LIST_COLS`, on the family infrastructure: `_FAMILY_COLS`, `_find_family_row` by `direction`) holds its own row — `mode` (`E`, `D`, `E+D`), BidType(394)/ListExecInstType(433) names and codes, `tot_no_orders` (68), `status` (ListOrderStatus(431) by name, Sent/Received before one), `status_type` (429), the request slot `pending_action` (New/Execute/Cancel), texts, `last_order_at`, `raw_message`. Its orders are `fix_orders` rows with `list_id` and `list_seq_no` (67; written once like the instrument, `_NO_LIST`), numbered by arrival when a message carries no 67. `lists_query` counts them (`orders`, `done_orders`, `pending_orders`, `filled_qty`) and carries them as the New List grid takes them (`list_orders`, JSON; Clone opens on it, an instrument by the saved name matching it), re-run by `watch_columns` on fix_orders.

- **Sending** — `send_new_list(orders, mode, bid_type, exec_inst_type, tot_orders, text, extra_tags, client)`: `orders` is the grid's JSON (or dicts) — New dialog terms, a saved instrument's name as `instrument` (its terms under what the row typed). Each order is built as a NewOrderSingle (instrument, client, list and own extras, `text`) and written, the list row with them, before anything is sent. **E** from 4.2 (`defines("394")`): one NewOrderList, `factory.new_order_list` putting each order's body (`lists.member_pairs`, ClOrdID then 67) in NoOrders(73) in the dictionary's member order; before 4.2, one NewOrderList a member with 66/67/68 in its body. **D**: each order a D with 66 (and 68 when `tot_orders`), no 67. A failed send rejects what did not go out (a list nothing reached is `Failed`).
- **Joining** — a D carrying 66, sent (`send_new_order(list_id=)`, `add_list_order`, or `66=` in the extras) or received (`_handle_new_order`), joins its list through `_join_list`, which makes the row if none (mode D), turns an E list's mode into `E+D`, stamps `last_order_at`, and parks `New` on a received list with nothing pending. A received order of a ListID is its list's whenever it comes; only archiving closes a list. Events `list`/`list joined` (received), `sent list`, and the orders' own.
- **Receiving** — E (`_handle_new_order_list`): the list row (mode E, its terms), then each member through `_handle_new_order` as the D it stands for (`lists.list_members` splits 73 at each ClOrdID, dictionary-free — 5.0SP2's group is ragged; `member_message`). N (`_handle_list_status`): a sent list's status, status type, 444; it clears an Execute answered by 431 Executing/AllDone/Reject and a Cancel by AllDone/Reject or 429 AllDone. Orders keep what their ERs said. L/K (`_handle_list_request`) park in the slot; M (`_handle_list_status_request`) is answered at once from the tables (429 Response, 73 reports: 11/14/39/151/84/6 where defined). An L, K or M naming no list gets a ListStatus Reject "Unknown list".
- **Client actions** — `execute_list` (L), `cancel_list` (K, or — `as_orders`, the default for D — `send_cancel` for each working order), `request_list_status` (M); L and K fill the slot (`_send_list_request`).
- **Market actions** — `accept_list`/`reject_list` answer the slot (or orders pending New): New accepts/rejects each pending order (`accept_order`/`reject_order`) and, for a NewOrderList, sends ListStatus Ack with 431 ReceivedForExecution (433=2) or Executing — or Reject; Execute → ExecStarted/Executing; Cancel → each working order `unsolicited_cancel`, then AllDone. `send_list_status` (unsolicited, Alert by default), `fill_list` (every working order for its leaves at its limit or the given price; none without a price), `cancel_list_orders`. Market ERs for a list's order carry 66 (`_stamp_order`).
- **UI** — Sent Lists / Received Lists (mkui 1.24's grid in New List…, Clone, Add Order…); the list ops are `UNSCRIPTED` until 0.78 gives them verbs. `tests/test_lists.py`, `TestListBlotters`.

## IOIs, adverts and allocations: `families.py`

Three more message families on the order model, each a chain of IDs: an IOI (35=6) is New/Replace/Cancel by IOITransType(28) with IOIRefID(26) naming the one superseded, an Advertisement (35=7) the same by AdvTransType(5)/AdvRefID(3), an AllocationInstruction (35=J; *Allocation* through 4.2) by AllocTransType(71)/RefAllocID(72). Only the allocation is answered — an AllocationInstructionAck (35=P) carrying AllocStatus(87) and, refused, AllocRejCode(88) — so only it has a request slot; nothing answers an IOI or an advert (the response to an IOI is an order carrying its ID in tag 23, which `fix_orders.ioi_id` records on both sides and `_link_ioi_order` writes back onto the IOI row's `order_cl_ord_id`; 23 is a consumed order tag). `families.py` is the pure part: `ioi_columns`/`advert_columns`/`allocation_columns`/`ack_columns` map a message to its row's term columns; `group_instances` reads a repeating group off the ordered wire pairs (the dictionary's member list says where an instance ends, `members` which tags the row keeps) and `group_pairs` writes one; an allocation's three groups (`ALLOC_GROUPS`: orders 73 → 11/37, executions 124 → 17/32/31, accounts 78 → 79/80/366) are kept as lines — `parse_lines`/`format_lines`, one instance per line or `;`, members by comma or space, the form the dialogs' textareas take and the cells show. The factory's `ioi`/`advertisement`/`allocation_instruction`/`allocation_ack` emit version-correct wire (626 from 4.3, 366 from 4.2, the IOI's 60 from 4.3, 25/130/199 where defined; groups ride on `extra` after the body, before the user's extras).

`fix_iois`, `fix_adverts`, `fix_allocations` (`IOI_COLS`/`ADVERT_COLS`/`ALLOC_COLS`): one row per chain, versioned, the ID column the chain's latest ID and `*_ref_id` the one before, split by `direction` into a Sent and a Received blotter. Generic ops `insert_<table>`/`update_<table>` (by row id, everything but session/direction/`timestamp`), `_find_family_row` (newest row holding an ID, per direction), `_sent_family_row` (columns from the message as sent — `_as_sent`, extras applied), `_received_family_row`. Inbound: `_handle_ioi`/`_handle_advertisement` insert a New, rewrite the row a Replace names (its terms), mark the one a Cancel names Canceled (terms kept); a reference matching nothing starts a row. `_handle_allocation`: a New parks as `PendingNew`/`pending_action` New; a Replace/Cancel (71=1/2) parks in the slot of the row 72 names — `pending_alloc_id` the request's 70, `pending_terms` its columns as JSON (a Cancel's only its identity and message), `pending_extra_tags` — under the session's order lock; one naming no row is answered at once with 87=1/88=7 "Unknown allocation". `_handle_allocation_ack` answers a sent row by the chain's current ID (the New, or an ack again) or by `pending_alloc_id`: accepted (87 in `ALLOC_ACCEPTING`: 0/3/4) the slot's terms and ID move onto the row (`_promoted_allocation`), Canceled for a Cancel; refused the row keeps them; both record `alloc_status`/`alloc_rej_*`/`text` (theirs) and `ALLOC_STATUS_OF` gives `status`. Actions (`SUBJECT_KEY`/`CREATES` naming their rows for `perform`'s event; `UNSCRIPTED` in actions.py is empty: every op has its verb): `send_ioi`/`replace_ioi`/`cancel_ioi` and the advert three write the row first, a Replace renaming it at once (nothing answers) and a Cancel keeping its terms, with the previous row put back if the send fails (`_send_family_message`; a new row that fails to go out is `Failed`); `send_allocation` (status `Sent`), `replace_allocation`/`cancel_allocation` park in the slot until the Ack (a failed send clears it); `accept_allocation`(`alloc_status` 0/3/4)/`reject_allocation`(1/2/5, `alloc_rej_code`) are `_market_action`s over the received row's slot, answering the request's ID, an accepted Replace/Cancel renaming the chain as the ER path does for orders, `sent_text` ours. IDs `IO`/`AD`/`AL`. Allocate (Received Orders) reads the order's live fills through the `order_fills` reqrep — a `_fills` pick whose `fill` copies executions-as-lines, total and average onto the form, remembered so the next open fills at once; Sent Trades' Allocate allocates the one trade. Events: `ioi`/`ioi replaced`/`ioi canceled`, `advert …`, `allocation`/`allocation replace`/`allocation cancel`, `allocation accepted`/`received`/`incomplete`/`rejected` then `allocation acked` (every Ack, as every ER is `er`), `sent ioi`/`sent advert`/`sent allocation` (with `source` and the macro's `tag`, as `sent order`), each with `table`/`row` and no `order`; the macro runner routes them by `(kind, row id)` with the family's name dropped from the kind. `_backfill_families` (fix_settings `families_backfill`) re-derives the pre-0.63 viewer rows from `raw_message` and folds a Replace/Cancel into the row it names. `tests/test_families.py` covers all of it; `TestFamilyBlotters` the panes.

## RFQs and quotes: `families.py`, engine.py

`fix_rfqs` (`RFQ_COLS`) holds one row per negotiation. There are two kinds, told apart by `origin`:

- **`rfq`**: a QuoteRequest (35=R) and the quotes that answer it.
- **`quote`**: unsolicited quotes on one instrument.

The row's quote columns hold the quote standing now. A requote is a new version of the row, so the row's history is the negotiation. `direction` is who opened the row. A side owns two kinds of rows (`quote_side`): the client's are sent RFQs and received quotes, the market's the other two. `_find_family_row` takes `client`/`market` in place of a direction to select them, and `SUBJECT_KEY` names the side the same way.

**Pure part** (families.py): `rfq_columns`, `quote_columns`, `response_columns`, and the `CONSUMED_*_TAGS` sets.

**Factory:**
- `quote_request` puts the instrument in the body through FIX 4.1, and in one NoRelatedSym(146) instance from 4.2. That instance also carries 303/537/54/38/15/60 where they are defined.
- `quote` sends 537 from 4.3, 54/38 from 4.4, and 60/15 from 4.2.
- `quote_cancel` sends 298=1 with the symbol in 295.
- `quote_request_reject` carries 658 and the 146 group.
- `quote_response` carries 693/117/694; a Hit adds 11/54/38/40/44.
- The engine refuses a message the session's dictionary lacks (`_require_message`): Z before 4.2, AG before 4.3, AJ before 4.4.

**Inbound:**

| Message | Handler | Effect |
|---|---|---|
| R | `_handle_quote_request` | opens an Open row |
| S | `_handle_quote` | quotes or requotes the row its 131 names, else the live unsolicited chain on its symbol (`_live_quote_chain`: status Quoted/Countered), else opens a `quote` row. A quote on a finished row (`FINAL_RFQ`) keeps that row's status |
| Z | `_handle_quote_cancel` | 298=4 cancels every live quote; otherwise the quote its 117 or 131 names, else the symbols in its 295 group |
| AG | `_handle_quote_request_reject` | rejects the RFQ |
| AI | `_handle_quote_status_report` | records 297; a status in `QUOTE_STATUS_ENDS` ends the quote |
| AJ | `_handle_quote_response` | see below |

On a QuoteResponse (AJ):
- **Counter** parks in the slot (`pending_*`), status Countered.
- **Hit with an 11** becomes a received order through `_handle_new_order` (`_order_from_response` fills side, size and price from the quote, 40=D).
- **Anything else** sets the status by `status_of_response`.

Every handler but R's holds the order lock.

**Orders naming a quote.** Tag 117 is a consumed order tag, recorded as `fix_orders.quote_id`. `_link_quote_order` marks the quote Hit and stores `order_cl_ord_id`, on both sides (sent orders by `send_new_order`).

**Actions** (`CREATES`/`SUBJECT_KEY` as for the other families):

| Side | Action | What it does |
|---|---|---|
| Client | `send_rfq` | writes the row, then announces `sent rfq`, before the send |
| Client | `hit_quote` | AJ Hit; writes the sent order (`_sent_order_row`, shared with `send_new_order`) and announces `sent order`; a failed send puts the quote back and rejects the order |
| Client | `counter_quote` | parks our counter in the slot |
| Client | `pass_quote` | |
| Market | `quote_rfq`, `requote` | `_market_action`s; clear the slot, since a requote answers a counter |
| Market | `reject_rfq`, `cancel_quote` | `_market_action`s |
| Market | `send_quote` | replaces the live chain on its symbol or opens a row |

**Validity and expiry.** `valid_for` (seconds) or `valid_until` becomes 62. `expire_due_quotes` marks Expired every Quoted/Countered row whose 62 has passed (source `engine`, nothing on the wire). `_expire_quotes` is the timer: started by `start`, stopped by `stop`, woken by `_wake_expiry`, sleeping at most a minute.

**Events** are `<origin> <what>`: `rfq`, `rfq quoted`, `rfq requoted`, `rfq countered`, `rfq hit`, `rfq passed`, `rfq rejected`, `rfq canceled`, `rfq expired`, `rfq status`, `rfq response`, the same with `quote`, plus `sent rfq` and `sent quote`.

**RFQ requests** (35=AH, FIX 4.3+) are kept on `fix_rfq_requests` (`RFQ_REQUEST_COLS`), one row per RFQReqID(644):
- The market side sends them (`send_rfq_request`: instruments by `parse_symbols`, 263 = 0 snapshot or 1 subscribe; `unsubscribe_rfq_request`: the same 644 and instruments with 263=2), and the client side receives them (`_handle_rfq_request`: an unsubscribe closes the row its 644 names).
- The factory's `rfq_request` sends one 146 instance per instrument (303/537 in each) and then 263. `rfq_request_columns` keeps the instruments as `symbols` (`; `-joined).
- Nothing answers a request. A QuoteRequest carrying 644 (consumed, `fix_rfqs.rfq_req_id`) is counted on the request's row by `_link_rfq_request` — the row we sent for a received RFQ, the row we received for a sent one — in `quote_requests` and `last_quote_req_id`.
- Events: `rfq request`, `rfq request unsubscribed`, `sent rfq request`. IDs `RR`; template scopes `rfq_request` and `unsubscribe`.

**IDs** are `RQ`/`QT`/`QR`.

**Templates:** the scopes are `rfq`, `quote`, `new_quote`, `quote_reject`, `hit`, `counter` and `pass`; `cancel_quote` shares `cancel`.

**Macros:** every op has its verb since 0.73 (macro/CLAUDE.md). `_link_rfq_request` also emits `rfq request answered`.

**Tests:** `tests/test_rfqs.py`; `TestRfqBlotters` covers the panes.

## Message Replay: `replay.py`

A job (`fix_replay_jobs`, `REPLAY_JOB_COLS`/`REPLAY_CONFIG_COLS` in engine.py) is a log file read once by `load_replay` (in a thread — a day's log; a path, or `example:<name>` naming a file in `replay_examples/`, resolved by `resolve_path`, which pins the name inside the folder): `parse_log_file` takes the four line shapes (prefix + message, ISO prefix, raw SOH, raw pipe), skips `#` lines and drops `ADMIN_MSG_TYPES`, and `summarize` puts the CompID pairs (first-appearance order), types with counts and dictionary names (by the first BeginString), and time span on the row as JSON `summary` with readable `pairs`/`first_time`/`last_time`. The two reqreps `replay_directions`/`replay_types` read it with `json_each` for the Start and Configure dialogs; `msg_filter` starts as every type, ticked. `configure_replay` validates (session known, numbers, window as `HH:MM[:SS]`, types in the file) and recomputes `default_direction` (`_default_direction`: the only pair, else the one pair whose sender is the session's SenderCompID — never the target's, which would play the counterparty out of our session). **The direction is asked at every Start** (`start_replay(job_id, direction)`; blank falls back to the default, and a two-way file with no default is refused) — the venue's side into an acceptor is a supported use. `select_messages` narrows by direction key (`SENDER→TARGET`, `direction_key`; blank for header-less lines, which form one blank pair), types and the log's time of day (unstamped messages pass), and `begin_replay` records the choice and count.

On the wire a replayed message is the session's: `prepare_for_send` drops `SESSION_TAGS` (8/9/10/34/49/56/52 — sendprep stamps them) and `DROPPED_TAGS` (43/122/369, the log's sequence space), restamps `RESTAMPED_BODY_TAGS` (60) with the send time at the session's precision, keeps every other header/trailer tag as a field (routing tags 50/57/115/116/128/129/142–145 ride in the dictionary's header order) and carries the body as ordered pairs on `extra`, so repeating groups survive (`fields` is a dict). The pre-0.54 bug was `sendprep` preferring a header tag already in `fields`, so a production log went out with its own CompIDs and MsgSeqNum. Pacing: the prefix, else 52, else 60; `ReplayTask.delay_before` divides the gap by `speed` (0 = none) and caps it at `max_gap` (0 = no cap); a pause landing during the sleep is honoured before the send. Progress writes go through the writer (`update_replay`), so the pane is live; `_replay_tasks` is stopped by `FixEngine.stop`, and `check_archive` refuses a playing job. The pane is a declarative `mkio-table` over `replay_jobs` (which LEFT JOINs `fix_session_state` for `session_status`, orders_query's way) with Load…/Configure…/Start… dialogs and one-click Pause/Resume/Stop/Delete, every op a `fix_cmd` command; `TestReplayControl` pins the Load dialog's example list to the files. `tests/test_replay_e2e.py` plays `two-sided-day` both ways over a linked stub pair.
